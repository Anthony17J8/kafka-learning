# Этап 3 — FAQ

Вопросы, возникшие в ходе практики. Базовые механизмы (poll-loop, коммиты,
таймауты, семантика доставки) разобраны в `THEORY.md` — здесь только то,
что из него не выводится напрямую.

---

## 1. Как работают стратегии назначения партиций?

Стратегия — алгоритм, решающий «какому консьюмеру какие партиции».
Пример: два топика по 3 партиции, два консьюмера, оба подписаны на оба топика.

### RangeAssignor (по умолчанию)

Работает **по каждому топику отдельно**: партиции сортируются, консьюмеры
сортируются, партиции нарезаются диапазонами.

```
orders:  P0 P1 P2  →  C1 = P0,P1   C2 = P2
users:   P0 P1 P2  →  C1 = P0,P1   C2 = P2

Итого: C1 = 4 партиции, C2 = 2
```

Перекос возник потому, что 3 не делится на 2, а остаток **каждый раз**
достаётся первому. С десятью топиками перекос вырастет вдесятеро.

Зачем такая стратегия: она гарантирует, что `orders-P0` и `users-P0` попадут
одному консьюмеру — упрощает join двух топиков по одному ключу на стороне
приложения. Ради этого свойства терпят перекос.

### RoundRobinAssignor

Все партиции всех топиков в один список, раздача по кругу.

```
C1: orders-P0, orders-P2, users-P1
C2: orders-P1, users-P0, users-P2      → 3 и 3, равномерно
```

Честнее, но связь «одинаковый номер партиции → один консьюмер» теряется.

### StickyAssignor

Добавляет второе требование: **при ребалансировке двигать минимум партиций**.

```
Было:   C1 = P0,P1,P2   C2 = P3,P4,P5.   Пришёл C3.

Не-sticky:  C1 = P0,P3  C2 = P1,P4  C3 = P2,P5   (переехало 4)
Sticky:     C1 = P0,P1  C2 = P3,P4  C3 = P2,P5   (переехало 2)
```

Критично для stateful-обработки: переезд партиции означает выброс накопленного
состояния и построение заново.

### CooperativeStickyAssignor

То же плюс cooperative-протокол ребалансировки (см. вопрос 3).
Рекомендуемый выбор для classic-протокола.

В новом протоколе (KIP-848) стратегию считает брокер — клиентская настройка
`partition.assignment.strategy` не применяется, вместо неё `group.remote.assignor`.

## 2. Что такое «идемпотентность приёмника»?

Идемпотентная операция даёт тот же результат при повторном выполнении,
что и при однократном.

При at-least-once вы **гарантированно** иногда обработаете запись дважды.
Значит обработка должна быть устроена так, чтобы дубль не портил результат.

**Не идемпотентно:**
```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
```
Дважды — списали 200.

**Идемпотентно:**
```sql
INSERT INTO orders (id, status) VALUES ('order-42', 'PAID')
ON CONFLICT (id) DO UPDATE SET status = 'PAID';
```
Дважды — результат тот же.

Три типовых способа:

**Upsert вместо insert.** Пишем «состояние должно быть таким», а не
«прибавь столько-то». Работает, когда событие несёт полное состояние.

**Дедупликация по ID события.** Храним обработанные `eventId`, проверяем перед
обработкой. Работает всегда, требует хранилища и его чистки.

**Условная запись с версией.** `UPDATE ... WHERE version < :newVersion`.
Повторное применение старой версии не проходит по условию.

Это тема этапа 11 (`IdempotentConsumer`). EOS внутри Kafka не распространяется
на внешние системы — за их пределами идемпотентность обеспечиваете вы.

## 3. Как работает ребалансировка?

Задача: партиции должны быть распределены между живыми консьюмерами группы.
Состав меняется — распределение надо пересчитать и договориться о нём.

### Eager-протокол, по шагам

1. **Триггер** — консьюмер вошёл, вышел или перестал слать heartbeat.
2. **Все отдают ВСЕ партиции.** Вызывается `onPartitionsRevoked` у каждого.
   С этого момента группа не обрабатывает данные.
3. **JoinGroup** — каждый шлёт координатору заявку на участие.
4. **Лидер считает назначение.** Координатор выбирает одного из **консьюмеров**
   лидером, тот применяет стратегию и шлёт результат в SyncGroup.
5. **Раздача** — `onPartitionsAssigned`, обработка возобновляется.

Шаги 2–4 это простой **всей группы**, включая тех, чьи партиции никуда не едут.
Группа из 20 консьюмеров: добавили 21-го — переедут пара партиций, встанут все.

### Cooperative

Отдаются **только переезжающие** партиции. Ребалансировка в два раунда:
первый вычисляет, что освободить, второй раздаёт. Консьюмеры, чьи партиции
не затронуты, работают без паузы.

```
Было: C1=[P0,P1] C2=[P2,P3] C3=[P4,P5], приходит C4

eager:        все трое отдали всё, простаивают 6 партиций
cooperative:  C3 отдал P5, C1 и C2 работают, простаивает 1 партиция
```

### KIP-848 (GA в Kafka 4.0)

Два отличия сверх cooperative:

**Назначение считает брокер**, а не выбранный консьюмер-лидер. Роль лидера
упразднена — клиент больше не делает работу за кластер.

**Нет глобального барьера синхронизации.** В classic все проходят
JoinGroup → SyncGroup вместе, группа движется со скоростью самого медленного.
В KIP-848 heartbeat одновременно сообщает состояние и приносит назначение,
каждому в своём темпе.

### Эмпирическое подтверждение из практики

Логи задачи 2 (classic, RangeAssignor) при добавлении 4-го консьюмера:

```
C1 REVOKED: [orders-1]     ← отдали ВСЕ,
C2 REVOKED: [orders-0]        хотя переезжала одна партиция
C3 REVOKED: [orders-2]
```

И ни одна партиция не осталась у прежнего владельца — Range не sticky,
пересчитывает с нуля.

На `group.protocol=consumer` при добавлении 2-го консьюмера первый отдал
**2 из 3** партиций — третью не отпускал вовсе.

## 4. Почему нельзя смешивать `subscribe` и `assign`?

Два режима на противоположных предпосылках.

**`subscribe`**: «я участник группы, распредели мне партиции сам». Heartbeat,
ребалансировки, набор партиций **меняется** по решению координатора.

**`assign`**: «я сам знаю, что читать, вот список». Ни группы, ни heartbeat,
набор **фиксирован**, меняется только вашим кодом.

Конфликт: если координатор считает, что вправе забрать партиции, а вы назначили
их вручную и отдавать не собираетесь — кто прав? Однозначного ответа нет,
поэтому такое состояние запрещено.

Технически: `assign()` после `subscribe()` (или наоборот) без `unsubscribe()`
бросает `IllegalStateException`. Проверка в клиенте, не на брокере.

Практически: сервис в группе — `subscribe`; утилита или разбор инцидента —
`assign`. Нужно и то и другое — два разных экземпляра.

## 5. Зачем и `fetch.max.bytes`, и `max.poll.records`?

Ограничивают **разные стадии**:

```
Брокер --[fetch.max.bytes]--> буфер консьюмера --[max.poll.records]--> ваш код
```

`fetch.max.bytes` (50 МБ) — сколько байт брокер отдаст за один **сетевой** ответ.
`max.partition.fetch.bytes` (1 МБ) — потолок на каждую партицию внутри ответа.
`max.poll.records` (500) — сколько записей вернёт один `poll()` **из буфера**.

`poll()` может отдавать записи без сетевого запроса: скачали 50 МБ одним fetch,
потом десять `poll()` выдают по 500 записей из памяти.

### Зачем нужен именно max.poll.records

Не ради памяти, а ради `max.poll.interval.ms`. Время обработки батча
пропорционально числу записей:

```
500 × 20 мс   = 10 секунд   → влезаем в 5 минут
500 × 2 сек   = 16 минут    → вылетаем из группы
```

Во втором случае лечение — уменьшить `max.poll.records` до 50, а не увеличивать
таймаут.

### При тяжёлых сообщениях max.poll.records не активен

Верно. При записях по 1 МБ упрётесь в `max.partition.fetch.bytes` раньше,
чем в счётчик записей. При мелких (сотни байт) байтовые лимиты недостижимы,
и основным регулятором становится `max.poll.records`.

**Работает тот лимит, который срабатывает первым.** Посчитайте средний размер
записи и прикиньте, какой у вас активен — крутить неактивный бесполезно.

## 6. Как выполняется fetch по нескольким партициям?

Fetch группируется **по брокерам**, а не по партициям. Один запрос уходит
одному брокеру и включает все партиции, лидером которых он является.

```
P0, P3 → kafka-1     FetchRequest → kafka-1: { P0: off 1500, P3: off 890 }
P1, P4 → kafka-2     FetchRequest → kafka-2: { P1: off 2100, P4: off 340 }
P2, P5 → kafka-3     FetchRequest → kafka-3: { P2: off 990,  P5: off 1720 }
```

Три запроса параллельно, ответы независимы.

**Партиционный лимит нужен для справедливости.** Без `max.partition.fetch.bytes`
одна активная партиция забила бы весь ответ, остальные голодали бы.

**Обход по кругу.** Когда данных больше, чем влезает в лимиты, брокер ротирует
порядок партиций между запросами — чтобы одни и те же не оказывались вечно
в конце. То же на стороне консьюмера при выдаче из буфера.

**Запись больше лимита отдаётся целиком.** Иначе тупик: не влезает → не
отдаётся → оффсет не двигается → следующий запрос упирается в неё же.
Байтовые лимиты «мягкие».

**Prefetch.** Пока вы обрабатываете батч, консьюмер уже отправил следующие
fetch-запросы. Число fetch-запросов и число вызовов `poll()` не связаны.

Практический вывод: неравномерный рост lag по партициям может объясняться
не обработкой, а тем, что партиции с большим объёмом упираются
в `max.partition.fetch.bytes`.

## 7. Насколько велик таймаут в `poll(Duration)`? Он ограничивает размер батча?

Нет. `poll(Duration.ofSeconds(2))` — «жди появления данных максимум 2 секунды».
Если данные уже в буфере, `poll()` вернётся **немедленно**. Это потолок
ожидания, не пауза перед выдачей.

Размер батча ограничивают `max.poll.records` (500 по умолчанию) и байтовые
лимиты — см. вопрос 5.

### Почему в SeekingConsumer 2 секунды, а в ManualCommitConsumer 500 мс

`SeekingConsumer` — разовая утилита, читает историю и должна сама остановиться.
Признак конца — три пустых `poll()` подряд. Длинный таймаут нужен для
**надёжности определения конца**: при `poll(100)` пустой результат может
означать «fetch-ответ ещё не долетел», и вы завершитесь преждевременно.

`ManualCommitConsumer` — долгоживущий сервис в группе. Callback'и rebalance
listener вызываются **внутри `poll()`**, поэтому длинный таймаут = поздняя
реакция на ребалансировку. Плюс `wakeup()` при длинном таймауте дольше
не замечается.

**Правило:** сервис в группе — 100–500 мс; утилита с определением конца
данных — 1–5 секунд. Размер батча регулируется не таймаутом, а
`max.poll.records`.

## 8. Замер ребалансировки показал 503 мс на KIP-848 и 50 мс на classic. Почему?

Артефакт замера. 503 мс подозрительно близко к `poll(Duration.ofMillis(500))` —
и это не совпадение.

Callback'и вызываются **внутри `poll()`**. При incremental-протоколе revoke
и assign разнесены по разным раундам, поэтому между ними обязательно
вклинивается ожидание `poll()`. При eager они могут произойти в рамках
**одного** вызова: отдал всё, прошёл JoinGroup/SyncGroup, получил обратно —
без выхода из `poll()`.

То есть сравнивается «одна фаза внутри одного poll» с «две фазы через два poll».
Разница в 450 мс — чистое ожидание, а не работа протокола.

Проверка: поставьте `poll(Duration.ofMillis(100))`. Если 503 превратится
в ~100 — подтверждено.

### Как мерить корректно

**Уменьшить таймаут poll** до 50–100 мс на время эксперимента.

**Мерить простой обработки:** время между последней обработанной записью
до ребалансировки и первой после. Это то, что реально волнует.

**Мерить со стороны группы:** запустить ровный поток и смотреть на суммарный
lag во время ребалансировки (`LagMonitor`). При eager lag подскочит на всех
партициях, при KIP-848 — только на переезжающих.

### Главный результат — не время, а число партиций

| Протокол | Отдал при добавлении 2-го консьюмера |
|---|---|
| classic (eager) | 3 из 3 — вся работа встала |
| consumer (KIP-848) | 2 из 3 — одна партиция читалась без перерыва |

## 9. После задачи 1 оффсеты сдвинулись — нужно ли их сбрасывать?

Для задачи 2 (наблюдение за распределением партиций) — нет. Строки `ASSIGNED`
и `REVOKED` появляются независимо от наличия данных: консьюмер участвует
в группе, шлёт heartbeat и получает назначения, даже когда `poll()` возвращает
пустоту.

Обратите внимание: `auto.offset.reset=earliest` здесь не поможет — он работает,
только когда закоммиченного оффсета **нет**.

Если хочется видеть поток данных, три варианта:

**Продюсер в фоне** — самое простое.

**Сброс оффсетов** (только для остановленной группы):
```bash
./scripts/kafka.sh kafka-consumer-groups.sh \
  --group orders-manual-commit --topic orders \
  --reset-offsets --to-earliest --execute
```
Без `--execute` — режим предпросмотра. Есть варианты `--to-latest`,
`--to-offset N`, `--to-datetime`, `--shift-by -100`.

**Новая группа** через `-Dgroup.id=...`. Понадобится в задаче 4 для сравнения
протоколов, так что параметризовать стоит в любом случае.

Оффсеты неактивных групп удаляются через `offsets.retention.minutes`
(7 суток по умолчанию), так что одноразовые группы уберутся сами.

## 10. Продюсер и консьюмер используют разные сериализаторы — что будет?

`SerializationException` при десериализации, и консьюмер **умирает**: ошибка
вылетает из `poll()`, оффсет не сдвигается, при перезапуске он упрётся в ту же
запись снова. Классический **poison pill**.

Пример из практики: `FailoverProducer` пишет `String`/`String`,
а `ManualCommitConsumer` десериализует значение как `OrderEvent` через Jackson.

Решения для эксперимента: отдельный топик со строковым консьюмером, либо
использовать `SimpleProducer` (он уже пишет `OrderEvent` в `orders`), либо
параметризовать тип значения.

### Два урока

**Формат данных в топике — контракт, который Kafka не проверяет.** Брокер
хранит байты и не знает, что в них. Несовпадение вылезает у консьюмера,
в рантайме. Ровно эту проблему решает Schema Registry (этап 4).

**Одна битая запись останавливает партицию навсегда.** Лечится
`ErrorHandlingDeserializer` (превращает ошибку в `null` вместо исключения)
либо ручным try-catch с отправкой в DLQ (этап 6).

Полезный эксперимент: запишите строку в `orders` через
`kafka-console-producer.sh` и посмотрите, как консьюмер на ней падает.

## 11. Консьюмеры с одним group.id ведут себя как разные группы

Симптом «каждому назначились все партиции» означает, что они не видят друг
друга. Причины по убыванию вероятности:

**Rebalance storm.** Если консьюмеры выпадают по `max.poll.interval.ms`
(задача 7), группа не достигает устойчивого состояния. Каждый в момент своего
короткого пребывания видит себя единственным — остальные в это время выброшены.
Это не «разные группы», а быстро сменяющиеся составы одной.

**Фактически разные `group.id`.** После параметризации через
`System.getProperty` легко забыть флаг в одном из терминалов. Проверка:
```bash
./scripts/kafka.sh kafka-consumer-groups.sh --list
```

**Смешение протоколов.** Один на `classic`, другой на `consumer`.
Проверка состава группы:
```bash
./scripts/kafka.sh kafka-consumer-groups.sh --describe --group <id>
```

Чистая проверка: убрать `sleep`, вернуть нормальный `max.poll.interval.ms`,
задать одинаковый `group.id` и `group.protocol` явно во всех терминалах.

## 12. Rebalance storm: как лечить в продакшене?

Симптом из задачи 7: консьюмер получает партиции, не успевает обработать батч
в `max.poll.interval.ms`, выпадает, снова входит. Данные не обрабатываются,
при этом процесс жив и ошибок в привычном смысле нет.

В логах видно:

```
Time between subsequent calls to poll() was longer than the configured
max.poll.interval.ms, exceeded approximately by 15032 ms. Member will rejoin.
LOST: [orders-0, orders-1, orders-2]
```

Обратите внимание: сработал **`onPartitionsLost`**, а не `Revoked` — консьюмер
уже вне группы, коммитить нельзя, только очистить локальное состояние.

### Что делать

**Уменьшить `max.poll.records`** — первое и обычно достаточное. Батч меньше →
обработка быстрее → укладываемся в интервал.

**Не увеличивать `max.poll.interval.ms`** как первое средство. Это лечение
симптома: вы просто дольше не замечаете, что консьюмер не справляется.

**Вынести обработку в пул потоков** при объективно долгих операциях (внешний
API, тяжёлые вычисления). `poll()` вызывается регулярно, оффсеты коммитятся
вручную по мере готовности. Сложнее, но единственный вариант, когда обработка
одной записи занимает секунды.

**Проверить, не блокирует ли обработка** на внешнем ресурсе без таймаута —
частая причина «внезапного» шторма в продакшене.
