## 1. Проблема: у топика нет контракта

Kafka хранит `byte[]` и не знает, что в них. Продюсер сериализует по-своему,
консьюмер десериализует по-своему. Совпадут ли они — вопрос договорённостей
вне системы.

Пока сервис один, терпимо. Проблемы начинаются при изменениях:

| Изменение | Что произойдёт |
|---|---|
| Добавили поле в JSON | Консьюмеры на Jackson переживут (при `FAIL_ON_UNKNOWN_PROPERTIES=false`) |
| Переименовали поле | Консьюмеры молча получат `null` вместо значения |
| Сменили тип с числа на строку | `SerializationException`, консьюмер падает |
| Записали строку вместо JSON | **Poison pill**: оффсет упирается в битую запись навсегда |

Ключевое: о поломке вы узнаёте **от консьюмеров, в проде, постфактум**.
Никто не мешает записать в топик что угодно.

Это ровно та ситуация, с которой сталкиваются на этапе 3, когда продюсер
и консьюмер используют разные сериализаторы.

## 2. Что делает Schema Registry

Отдельный сервис, хранящий схемы и проверяющий совместимость **до записи**.

Поток при отправке:

1. Продюсер сериализует объект и передаёт схему в Registry
2. Registry проверяет совместимость с уже зарегистрированными версиями
3. При успехе возвращает числовой **schema id**; при провале — ошибку 409
4. Продюсер пишет в Kafka: `id + данные` (схема **не** дублируется)

Поток при чтении:

1. Консьюмер читает запись, извлекает schema id из первых байт
2. Запрашивает схему у Registry по id (при первой встрече; дальше из кеша)
3. Десериализует данные по этой схеме

Два свойства, которые это даёт:

**Проверка на входе.** Несовместимая схема отклоняется у продюсера, при деплое,
а не у консьюмера через неделю.

**Компактность.** В сообщении лежит 4-байтовый id, а не схема целиком.
Для JSON с длинными именами полей экономия существенная.

Сами схемы Registry хранит во внутреннем compacted-топике `_schemas` — то есть
Registry stateless, всё состояние в Kafka.

## 3. Формат сообщения на диске

Confluent wire format — 5 служебных байт перед полезной нагрузкой:

```
[0]      magic byte = 0
[1..4]   schema id, big-endian int32
[5..]    сериализованные данные (Avro binary / Protobuf / JSON)
```

Отсюда два практических следствия:

**Обычный консьюмер прочитает мусор.** `kafka-console-consumer.sh` без
указания Avro-десериализатора покажет первые байты как непечатаемые символы.
Для чтения нужен `kafka-avro-console-consumer` с `--property
schema.registry.url=...`.

**Magic byte позволяет отличить формат.** Значение 0 в первом байте —
признак Confluent-формата.

## 4. Avro — основы

### 4.1. Схема как JSON

```json
{
  "type": "record",
  "name": "OrderEvent",
  "namespace": "dev.kafkalearn.avro",
  "fields": [
    { "name": "orderId",  "type": "string" },
    { "name": "quantity", "type": "int" },
    { "name": "price",    "type": "double" },
    { "name": "currency", "type": "string", "default": "EUR" }
  ]
}
```

`namespace` + `name` образуют полное имя типа. Оно попадает в сгенерированный
Java-класс и участвует в проверке совместимости.

### 4.2. Типы

**Примитивы:** `null`, `boolean`, `int`, `long`, `float`, `double`, `bytes`, `string`.

**Сложные:** `record`, `enum`, `array`, `map`, `union`, `fixed`.

**Логические типы** — надстройка над примитивами:

```json
{ "name": "createdAt", "type": { "type": "long", "logicalType": "timestamp-millis" } }
{ "name": "amount",    "type": { "type": "bytes", "logicalType": "decimal",
                                 "precision": 12, "scale": 2 } }
```

### 4.3. Nullable-поля

В Avro нет отдельного «nullable». Nullable = union с `null`:

```json
{ "name": "discount", "type": ["null", "double"], "default": null }
```

Важно: **`null` должен быть первым** в union, если default равен null.
Avro берёт default из первого типа union.

### 4.4. Default — ключевое понятие этапа

`default` определяет, что подставить, если поля нет в данных. Именно на нём
держится вся эволюция схем.

```json
{ "name": "currency", "type": "string", "default": "EUR" }
```

Читая старые данные без `currency`, десериализатор подставит `"EUR"`.
Без `default` он не знает, что делать, — отсюда несовместимость.

### 4.5. Генерация Java-классов

Плагин `avro-maven-plugin` генерирует классы из `.avsc` при сборке:

```xml
<plugin>
  <groupId>org.apache.avro</groupId>
  <artifactId>avro-maven-plugin</artifactId>
  <executions><execution>
    <phase>generate-sources</phase>
    <goals><goal>schema</goal></goals>
    <configuration>
      <sourceDirectory>${project.basedir}/src/main/avro</sourceDirectory>
    </configuration>
  </execution></executions>
</plugin>
```

Получается класс с билдером:

```java
OrderEvent order = OrderEvent.newBuilder()
    .setOrderId("order-42")
    .setQuantity(3)
    .setPrice(199.99)
    .build();
```

Это **SpecificRecord** — типобезопасный вариант. Есть и **GenericRecord**,
где поля адресуются по имени как в мапе: гибче, но без проверок компилятора.

## 5. Эволюция схем и совместимость

### 5.1. Две схемы в каждом чтении

Avro всегда работает с парой:

- **Writer schema** — та, которой данные были записаны (по id из сообщения)
- **Reader schema** — та, которую ожидает читающее приложение

Десериализатор выполняет **schema resolution**: сопоставляет поля по имени
и приводит данные writer-схемы к reader-схеме. Совместимость — это вопрос
о том, возможно ли такое приведение.

### 5.2. Режимы

| Режим | Смысл | Порядок обновления |
|---|---|---|
| `BACKWARD` (по умолчанию) | Новая схема читает старые данные | Консьюмеры первыми |
| `BACKWARD_TRANSITIVE` | То же, но против **всех** прошлых версий | Консьюмеры первыми |
| `FORWARD` | Старая схема читает новые данные | Продюсеры первыми |
| `FORWARD_TRANSITIVE` | То же против всех версий | Продюсеры первыми |
| `FULL` | Оба направления | Любой |
| `FULL_TRANSITIVE` | Оба против всех версий | Любой |
| `NONE` | Проверки отключены | — |

Мнемоника: режим называется по тому, что делает **новая** схема.
BACKWARD — смотрит назад, читает старое.

Обычные (не транзитивные) режимы проверяют только против **последней** версии.
Транзитивные — против всех. Разница проявляется при цепочке изменений:
v1 → v2 совместимо, v2 → v3 совместимо, но v1 → v3 может быть несовместимо.

### 5.3. Какие изменения допустимы

| Изменение | BACKWARD | FORWARD | FULL |
|---|---|---|---|
| Добавить поле **с** default | да | да | да |
| Добавить поле **без** default | нет | да | нет |
| Удалить поле **с** default | да | да | да |
| Удалить поле **без** default | да | нет | нет |
| Переименовать поле | нет | нет | нет |
| Сменить тип | нет* | нет* | нет |
| Добавить значение в enum | нет** | да | нет |

\* Допустимы расширяющие приведения: `int` → `long`, `float` → `double`,
`string` ↔ `bytes`.

\** Разрешено, если у enum задан `default`.

Логика проще, чем таблица. При BACKWARD новая схема читает старые данные:
если поле добавили, в старых данных его нет — нужен default. Если удалили,
новая схема просто игнорирует лишнее поле в данных.

При FORWARD зеркально: старая схема читает новые данные. Добавленное поле
она проигнорирует. Удалённое — будет искать и не найдёт, поэтому нужен default
в старой схеме.

**Переименование не допускается никогда.** Для Avro это удаление одного поля
и добавление другого. Обходной путь — `aliases`:

```json
{ "name": "customerId", "type": "string", "aliases": ["userId"] }
```

### 5.4. Почему BACKWARD по умолчанию

В топике с retention в неделю лежат данные, записанные старой схемой.
Новый консьюмер должен уметь их прочитать — иначе перезапуск с начала топика
упадёт. Плюс типичный порядок деплоя: обновляем читателей, потом писателей.

FORWARD выбирают, когда консьюмеры вне вашего контроля — внешние потребители,
партнёрские интеграции, старые мобильные клиенты. Тогда важно, чтобы они
продолжали читать новые данные без обновления.

## 6. Subject и стратегии именования

**Subject** — область видимости, внутри которой версионируются схемы.
Один subject = одна линия версий = одна проверка совместимости.

Три стратегии (`value.subject.name.strategy`):

**TopicNameStrategy** (по умолчанию): `<topic>-value` и `<topic>-key`.
Одна схема на топик. Простейший и самый частый вариант.

**RecordNameStrategy**: полное имя типа Avro. Позволяет писать **разные типы**
событий в один топик — например, `OrderCreated`, `OrderPaid`, `OrderShipped`
в топик `orders`, каждый со своей линией версий.

**TopicRecordNameStrategy**: `<topic>-<полное имя типа>`. Комбинация: разные
типы в топике, но версионирование ограничено этим топиком.

Вторая и третья нужны, когда порядок между разными типами событий важен —
их приходится класть в одну партицию одного топика.

## 7. Avro против Protobuf против JSON Schema

| | Avro | Protobuf | JSON Schema |
|---|---|---|---|
| Формат на диске | бинарный | бинарный | текст |
| Компактность | высокая | высокая | низкая |
| Читаемость сырых данных | нет | нет | да |
| Схема нужна при чтении | **обязательно** | нет | нет |
| Эволюция | по именам полей | по номерам полей | по именам |
| Экосистема Kafka | родная | хорошая | базовая |

**Avro** — выбор по умолчанию в мире Kafka. Kafka Streams, Connect, ksqlDB
работают с ним лучше всего. Особенность: без схемы данные **вообще
не прочитать** — она обязательна при десериализации.

**Protobuf** — если он уже используется в компании (gRPC). Эволюция строится
на номерах полей, а не именах, поэтому переименование безболезненно, а вот
переиспользование номера — катастрофа.

**JSON Schema** — когда важна читаемость сырых данных или потребители
не умеют в бинарные форматы. Платите объёмом.

## 8. REST API Registry

```bash
SR=http://localhost:8081

# Список subject'ов
curl -s $SR/subjects | jq

# Версии subject'а
curl -s $SR/subjects/orders-value/versions | jq

# Конкретная версия
curl -s $SR/subjects/orders-value/versions/1 | jq
curl -s $SR/subjects/orders-value/versions/latest | jq

# Схема по id
curl -s $SR/schemas/ids/1 | jq

# Зарегистрировать схему
curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"schema": "{\"type\":\"record\",...}"}' \
  $SR/subjects/orders-value/versions | jq

# ПРОВЕРИТЬ совместимость, не регистрируя
curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"schema": "..."}' \
  $SR/compatibility/subjects/orders-value/versions/latest | jq

# Режим совместимости
curl -s $SR/config/orders-value | jq
curl -s -X PUT -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"compatibility": "FULL"}' $SR/config/orders-value | jq

# Глобальный режим по умолчанию
curl -s $SR/config | jq
```

Схема передаётся как **строка с экранированным JSON** внутри JSON — отсюда
громоздкие кавычки. Удобнее собирать через `jq`:

```bash
jq -n --rawfile s src/main/avro/order-event.avsc '{schema: $s}' \
  | curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
      --data @- $SR/subjects/orders-value/versions | jq
```

Эндпоинт `/compatibility/...` — самый полезный в разработке: проверяет
изменение, ничего не регистрируя. Его стоит вызывать в CI.

## 9. Настройки клиента

### Продюсер

```java
props.put(KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(VALUE_SERIALIZER_CLASS_CONFIG, KafkaAvroSerializer.class);
props.put("schema.registry.url", "http://localhost:8081");
props.put("auto.register.schemas", true);   // по умолчанию true
```

### Консьюмер

```java
props.put(VALUE_DESERIALIZER_CLASS_CONFIG, KafkaAvroDeserializer.class);
props.put("schema.registry.url", "http://localhost:8081");
props.put("specific.avro.reader", true);    // SpecificRecord вместо GenericRecord
```

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `schema.registry.url` | — | Адрес Registry, обязательна |
| `auto.register.schemas` | true | Регистрировать схему при первой отправке |
| `use.latest.version` | false | Использовать последнюю версию вместо своей |
| `specific.avro.reader` | false | Десериализовать в сгенерированный класс |
| `max.schemas.per.subject` | 1000 | Размер локального кеша |

**`auto.register.schemas=false` в проде.** Автоматическая регистрация удобна
в разработке, но означает, что любой продюсер может добавить версию схемы.
В продакшене схемы регистрируют через CI/CD, а приложениям оставляют только
чтение.

## 10. Эксплуатация

**Registry недоступен.** Продюсер не сможет отправить (нужен id), консьюмер
не сможет прочитать незакешированные схемы. Уже закешированные — прочитает.
Registry — критичная зависимость, разворачивают в нескольких экземплярах.

**Registry stateless.** Всё состояние в топике `_schemas`. Потеря инстанса
не страшна, потеря топика — фатальна. `_schemas` реплицируют с RF=3.

**Удаление схем.** Soft delete (`DELETE /subjects/X`) убирает из выдачи,
hard delete (`?permanent=true`) стирает окончательно. Осторожно: если
в топике остались данные, записанные удалённой схемой, их станет не прочитать.

**Совместимость нужно задавать явно.** Глобальный дефолт применяется только
к subject'ам без собственной настройки. Меняя глобальный, вы не меняете
существующие.

## 11. Ответы на контрольные вопросы

### 11.1. Почему BACKWARD — самый частый выбор?

В топике лежат данные, записанные старыми схемами (retention обычно дни или
недели). Консьюмер, читающий с начала, должен уметь их разобрать. BACKWARD
это гарантирует. Плюс он соответствует типичному порядку деплоя: сначала
обновляют читателей (они уже понимают обе версии), потом писателей.

### 11.2. Что в первых пяти байтах сообщения и зачем?

Байт 0 — magic byte, признак Confluent-формата. Байты 1–4 — schema id
в big-endian. По нему консьюмер запрашивает у Registry writer-схему, без
которой Avro-данные не разобрать. Схема целиком в сообщение не кладётся —
это экономит место и позволяет менять схемы, не переписывая данные.

### 11.3. Почему добавление поля без default ломает BACKWARD, но не FORWARD?

**BACKWARD**: новая схема читает старые данные. В старых данных нового поля
нет. Без default десериализатор не знает, чем его заполнить, — ошибка.

**FORWARD**: старая схема читает новые данные. Новое поле старой схеме
неизвестно, она его просто игнорирует. Проблемы нет.

Зеркально для удаления: при BACKWARD удаление безопасно (новая схема
игнорирует лишнее в данных), при FORWARD требует default в старой схеме.

### 11.4. Что произойдёт, если Registry недоступен?

**Продюсер** не сможет отправить: нужен schema id, а получить его неоткуда.
Если id уже в кеше (схема отправлялась раньше в этой сессии) — отправка
пройдёт.

**Консьюмер** прочитает записи со схемами из кеша. Встретив незнакомый id,
упадёт с ошибкой обращения к Registry.

Отсюда: Registry — критичный компонент, требует HA-развёртывания. Кеши дают
частичную устойчивость к коротким сбоям, но не заменяют доступность.

### 11.5. Как совместить порядок событий разных типов в одном топике?

`OrderCreated`, `OrderPaid`, `OrderShipped` для одного заказа должны идти
по порядку — значит, в одну партицию одного топика. Но TopicNameStrategy
допускает одну схему на топик.

Решение — `RecordNameStrategy` или `TopicRecordNameStrategy`: subject берётся
из имени типа, каждый тип версионируется отдельно, а физически они лежат
в одном топике.

Альтернатива — schema references: одна схема-union, ссылающаяся на несколько
типов. Сложнее в поддержке.
