## 1. Poll-loop — основная модель

Консьюмер работает циклом:

```java
consumer.subscribe(List.of("orders"));
while (running) {
    ConsumerRecords<K, V> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<K, V> record : records) {
        process(record);
    }
    consumer.commitSync();
}
```

`poll()` — не просто «забрать данные». Внутри него происходит:

- отправка fetch-запросов брокерам,
- получение и буферизация записей,
- **отправка heartbeat** (в classic-протоколе — фоновым потоком, но координация с poll есть),
- обработка ребалансировки (вызов listener'ов),
- автокоммит, если включён.

Отсюда фундаментальное свойство: **консьюмер жив, пока вызывает `poll()`**. Долгая
обработка между вызовами выглядит для группы как зависание.

### Однопоточность

`KafkaConsumer` **не потокобезопасен**. Один экземпляр — один поток. Попытка
вызвать методы из разных потоков даёт `ConcurrentModificationException`.

Исключение — `wakeup()`, единственный метод, который можно вызывать извне.
Он прерывает блокирующий `poll()`, бросая `WakeupException`. Штатный способ
корректно остановить консьюмер из shutdown hook.

Для параллелизма используют не потоки внутри консьюмера, а **несколько
консьюмеров в группе** (раздел 2) либо передачу записей в пул обработки
с ручным управлением оффсетами.

## 2. Consumer groups

### 2.1. Модель

Группа — набор консьюмеров с одинаковым `group.id`. Kafka делит партиции топика
между участниками так, что **одну партицию читает ровно один консьюмер группы**.

Следствия:

**Потолок параллелизма = число партиций.** Консьюмеры сверх этого числа
простаивают, не получая назначения.

**Группы независимы.** Разные `group.id` читают один топик, не мешая друг другу,
каждая со своими оффсетами. Это модель publish-subscribe поверх лога.

**Масштабирование горизонтальное.** Добавили инстанс — партиции перераспределились,
нагрузка поделилась. В пределах числа партиций.

### 2.2. Group coordinator

Для каждой группы один из брокеров назначается **координатором**. Выбирается так:

```
партиция = hash(group.id) % 50
координатор = лидер этой партиции __consumer_offsets
```

Координатор отвечает за: приём heartbeat, обнаружение выбывших участников,
запуск ребалансировки, хранение назначений и оффсетов.

### 2.3. Стратегии назначения (classic-протокол)

`partition.assignment.strategy`, по умолчанию `[RangeAssignor, CooperativeStickyAssignor]`.

| Стратегия | Логика | Особенность |
|---|---|---|
| `RangeAssignor` | Делит партиции каждого топика диапазонами | Перекос при подписке на несколько топиков |
| `RoundRobinAssignor` | По кругу через все партиции всех топиков | Равномернее, но не sticky |
| `StickyAssignor` | Минимизирует переезды при ребалансировке | Eager |
| `CooperativeStickyAssignor` | То же + cooperative-протокол | Рекомендуемый для classic |

В новом протоколе (KIP-848) стратегия задаётся на сервере через
`group.remote.assignor` — клиент больше не участвует в вычислении.

## 3. Оффсеты и коммиты

### 3.1. Что такое коммит

Коммит — запись в `__consumer_offsets` позиции, с которой группа продолжит чтение
после перезапуска или ребалансировки. Это **не** подтверждение обработки записи
брокеру, а закладка для самой группы.

Коммитится **следующая** позиция, а не последняя обработанная:

```java
new OffsetAndMetadata(record.offset() + 1)
```

Если обработали запись с оффсетом 42, коммитим 43 — «с этого места продолжать».

### 3.2. Автокоммит

`enable.auto.commit=true` (по умолчанию), `auto.commit.interval.ms=5000`.

Коммит происходит **внутри `poll()`**, если с прошлого коммита прошло больше
интервала. Коммитятся оффсеты записей, **возвращённых предыдущим `poll()`** —
независимо от того, обработаны они или нет.

Проблемы:

**Нет контроля над семантикой.** Сбой между автокоммитом и завершением обработки
теряет записи. Сбой до автокоммита их дублирует. Какой случай сработает —
зависит от тайминга.

**Скрытая потеря при ребалансировке.** Партиции могут уехать после автокоммита,
но до обработки.

Для любой обработки с побочными эффектами автокоммит выключают.

### 3.3. Ручной коммит

**Синхронный** — `commitSync()`. Блокируется до подтверждения, ретраит при
retriable-ошибках, бросает исключение при провале. Медленно, но надёжно.

**Асинхронный** — `commitAsync()`. Не блокируется, callback сообщает результат.
Быстро, но **не ретраит** — повторная попытка могла бы перезаписать более
свежий коммит более старым значением.

Типичный production-паттерн: `commitAsync()` в горячем цикле + `commitSync()`
в `finally` перед закрытием и в `onPartitionsRevoked`.

```java
try {
    while (running) {
        var records = consumer.poll(timeout);
        process(records);
        consumer.commitAsync();
    }
} finally {
    try {
        consumer.commitSync();   // финальный, с гарантией
    } finally {
        consumer.close();
    }
}
```

### 3.4. Где хранятся оффсеты

Внутренний топик `__consumer_offsets`: 50 партиций, `cleanup.policy=compact`.

- Ключ: `(group.id, topic, partition)`
- Значение: оффсет, метаданные, timestamp

Компакция здесь по назначению — нужен только последний коммит каждой группы.

`offsets.retention.minutes` (по умолчанию 10080, то есть 7 суток) — сколько
хранятся оффсеты группы после того, как она перестала быть активной. По истечении
группа считается новой, и при следующем старте применится `auto.offset.reset`.

### 3.5. auto.offset.reset

Что делать, если закоммиченного оффсета нет (новая группа) или он вне диапазона
(данные удалены по retention):

| Значение | Поведение |
|---|---|
| `latest` (по умолчанию) | Читать только новые записи |
| `earliest` | Читать с начала лога |
| `none` | Бросить `NoOffsetForPartitionException` |

Частая ошибка: новая группа с `latest` не видит существующих данных, и это
выглядит как «консьюмер не работает».

## 4. Семантика доставки

Определяется порядком двух операций: обработать и закоммитить.

### 4.1. At-least-once

```
poll → обработать → commit
```

Сбой между обработкой и коммитом → запись перечитается → **дубль**.

Потери невозможны. Это выбор по умолчанию для большинства задач.
Дубли лечатся идемпотентной обработкой (этап 11).

### 4.2. At-most-once

```
poll → commit → обработать
```

Сбой между коммитом и обработкой → оффсет уже сдвинут, запись не вернётся →
**потеря**.

Дубли невозможны. Применимо там, где потеря дешевле дубля: метрики, телеметрия,
логи.

### 4.3. Exactly-once

Внутри Kafka достигается транзакциями (этап 5): коммит оффсетов входит
в ту же транзакцию, что и запись результата. При записи во внешние системы
требуется идемпотентность приёмника.

## 5. Ребалансировка

### 5.1. Что её запускает

- Присоединение нового консьюмера к группе
- Выход консьюмера (штатный или по таймауту)
- Изменение числа партиций топика
- Изменение набора топиков при подписке по regex

### 5.2. Eager-протокол

Исторический механизм. При любом изменении:

1. Все консьюмеры отдают **все** партиции (`onPartitionsRevoked`)
2. Все шлют JoinGroup координатору
3. Координатор выбирает лидера — одного из консьюмеров
4. Лидер вычисляет назначение и шлёт координатору (SyncGroup)
5. Координатор раздаёт назначения
6. Все получают партиции (`onPartitionsAssigned`) и продолжают

Проблема — шаг 1: **вся группа останавливается**, даже те, чьи партиции
не переезжают. Stop-the-world. На больших группах пауза измеряется секундами
и десятками секунд.

### 5.3. Cooperative (KIP-429)

Incremental cooperative rebalancing. Ключевое отличие: консьюмеры отдают
**только те партиции, которые реально переезжают**.

Ребалансировка идёт в два раунда: первый вычисляет, что нужно отдать, второй
раздаёт освободившееся. Консьюмеры, чьи партиции не затронуты, работают без паузы.

Включается через `partition.assignment.strategy=CooperativeStickyAssignor`.

### 5.4. Новый протокол (KIP-848), GA в Kafka 4.0

Принципиальная переработка. Главные отличия:

**Назначение вычисляет брокер.** Координатор сам считает распределение
и рассылает его. Роль консьюмера-лидера упразднена.

**Нет глобального барьера синхронизации.** Каждый консьюмер получает своё
назначение независимо, по мере готовности. Отсюда исчезает «пауза всей группы».

**Новый RPC.** `ConsumerGroupHeartbeat` вместо связки JoinGroup/SyncGroup.
Heartbeat несёт и информацию о состоянии, и получает назначения.

**Таймауты переехали на брокер.** `session.timeout.ms` и `heartbeat.interval.ms`
теперь настройки группы на стороне сервера: `group.consumer.session.timeout.ms`,
`group.consumer.heartbeat.interval.ms`.

Включается на клиенте:

```java
props.put(ConsumerConfig.GROUP_PROTOCOL_CONFIG, "consumer");  // вместо "classic"
```

Смешанные группы поддерживаются: часть участников на classic, часть на новом
протоколе — для плавной миграции.

### 5.5. Rebalance listeners

```java
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) { }
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) { }
    public void onPartitionsLost(Collection<TopicPartition> partitions) { }
});
```

**`onPartitionsRevoked`** — вызывается перед потерей партиций. Здесь коммитят
оффсеты: партиции ещё ваши, коммит валиден. Пропустите этот шаг — новый владелец
перечитает уже обработанное.

**`onPartitionsAssigned`** — после получения партиций. Здесь инициализируют
состояние, при необходимости делают `seek()`.

**`onPartitionsLost`** — партиции отобраны принудительно (консьюмер выпал
из группы по таймауту). **Коммитить нельзя** — владелец уже сменился, коммит
затрёт чужой прогресс. Только очистить локальное состояние.

Различие между `Revoked` и `Lost` — одна из тонкостей, которую легко упустить.

## 6. Таймауты и heartbeat

Два независимых механизма обнаружения «мёртвого» консьюмера. Их путают чаще всего.

### 6.1. session.timeout.ms — процесс жив?

По умолчанию 45000 (45 секунд).

Консьюмер шлёт heartbeat координатору каждые `heartbeat.interval.ms`
(по умолчанию 3000). Не получил heartbeat дольше `session.timeout.ms` →
координатор считает участника выбывшим и запускает ребалансировку.

В classic-протоколе heartbeat отправляет **отдельный фоновый поток** (KIP-62).
Это важно: heartbeat идёт даже во время обработки записей.

Правило: `heartbeat.interval.ms` ≈ 1/3 от `session.timeout.ms`.

### 6.2. max.poll.interval.ms — обработка не зависла?

По умолчанию 300000 (5 минут).

Максимальное время между двумя вызовами `poll()`. Превышено → консьюмер
сам покидает группу, партиции переназначаются.

Зачем нужен отдельно от session timeout: heartbeat-поток продолжает работать,
даже если обработка зависла в бесконечном цикле или ждёт недоступную БД.
Формально консьюмер «жив», но данные не обрабатывает. `max.poll.interval.ms`
ловит именно этот случай.

### 6.3. Как их соотносить

| Симптом | Причина | Настройка |
|---|---|---|
| Процесс убит / сеть пропала | Heartbeat перестал идти | `session.timeout.ms` |
| Обработка одного батча слишком долгая | `poll()` не вызывается | `max.poll.interval.ms` |

Если обработка объективно долгая — два пути: увеличить
`max.poll.interval.ms` либо уменьшить `max.poll.records` (по умолчанию 500),
чтобы батч обрабатывался быстрее. Второе обычно правильнее.

Классический симптом неверной настройки: консьюмер бесконечно ребалансируется,
в логах чередуются revoke и assign. Означает, что обработка не укладывается
в `max.poll.interval.ms`.

## 7. Consumer lag

**Lag = (последний оффсет в партиции) − (закоммиченный оффсет группы)**

Сколько записей группа ещё не обработала. Метрика номер один для здоровья
потребления.

Интерпретация:

- Стабильный небольшой lag — норма, консьюмер поспевает
- **Растущий** lag — консьюмер не справляется с темпом продюсера
- Резкий скачок — сбой обработки, ребалансировка или всплеск трафика

Важно смотреть на **динамику**, а не абсолютное значение. Lag в 100 тысяч
при темпе миллион в секунду — секунда отставания. Lag в 100 при темпе
десять в секунду — десять секунд.

Способы получить:

```bash
kafka-consumer-groups.sh --bootstrap-server ... --describe --group my-group
```

Программно — через `AdminClient`: `listConsumerGroupOffsets()` даёт
закоммиченные позиции, `listOffsets()` с `OffsetSpec.latest()` — концы логов.

Метрики JMX консьюмера: `records-lag-max`, `records-lag` по партициям.
Их и выводят на дашборд (этап 9).

## 8. subscribe против assign

**`subscribe(topics)`** — участие в группе. Партиции назначает координатор,
работает ребалансировка, оффсеты коммитятся в `__consumer_offsets`.
Обычный режим для сервисов.

**`assign(partitions)`** — ручное назначение конкретных партиций. Ни группы,
ни ребалансировки, ни автоматического назначения. `group.id` не обязателен.

Когда нужен `assign`:

- Разбор инцидента: перечитать конкретную партицию с конкретного оффсета
- Инструменты и утилиты: подсчёт lag, экспорт данных
- Приложения со своей схемой распределения работы

Смешивать нельзя: `subscribe` и `assign` на одном экземпляре взаимоисключающи.

### seek и offsetsForTimes

С `assign` доступно точное позиционирование:

```java
consumer.seek(partition, offset);           // конкретный оффсет
consumer.seekToBeginning(partitions);       // начало
consumer.seekToEnd(partitions);             // конец
consumer.offsetsForTimes(timestampsToSearch); // оффсет по времени
```

`offsetsForTimes()` использует `.timeindex` из этапа 1. Возвращает `null` для
партиции, если записей позднее указанного времени нет.

## 9. Static membership

`group.instance.id` (KIP-345) — постоянный идентификатор инстанса.

Без него каждый перезапуск консьюмера выглядит для координатора как уход
одного участника и приход другого — две ребалансировки на каждый рестарт.

Со static membership координатор помнит инстанс по его id. Кратковременный
перезапуск (в пределах `session.timeout.ms`) не вызывает ребалансировку вовсе —
вернувшийся консьюмер получает те же партиции.

Полезно при роллинг-рестартах в Kubernetes, где под перезапускается регулярно
и партиции всё равно вернутся туда же.

Требование: id должен быть уникальным и **стабильным** между перезапусками
конкретного инстанса (например, из имени пода StatefulSet).

## 10. Настройки fetch

Управляют тем, как консьюмер забирает данные с брокера.

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `fetch.min.bytes` | 1 | Минимум данных в ответе; брокер ждёт накопления |
| `fetch.max.wait.ms` | 500 | Сколько брокер ждёт накопления `fetch.min.bytes` |
| `fetch.max.bytes` | 52428800 (50 МБ) | Максимум на один fetch-запрос |
| `max.partition.fetch.bytes` | 1048576 (1 МБ) | Максимум на партицию |
| `max.poll.records` | 500 | Сколько записей вернёт один `poll()` |

`fetch.min.bytes` — зеркало `linger.ms` продюсера: увеличив его, получите
меньше запросов и выше throughput ценой задержки.

`max.poll.records` не влияет на сеть — это ограничение на то, сколько записей
`poll()` отдаст приложению за раз. Напрямую связано
с `max.poll.interval.ms`: чем больше батч, тем дольше его обработка.

## 12. Ответы на контрольные вопросы

### 12.1. Разница между `session.timeout.ms` и `max.poll.interval.ms`

`session.timeout.ms` ловит **мёртвый процесс**: heartbeat перестал приходить,
значит консьюмер убит или потерял сеть. Heartbeat шлёт отдельный фоновый поток,
поэтому работает независимо от обработки.

`max.poll.interval.ms` ловит **зависшую обработку**: процесс жив, heartbeat идёт,
но `poll()` не вызывается — обработка застряла. Формально участник в группе,
фактически не работает.

Два разных отказа, два разных механизма.

### 12.2. Почему коммитим `offset + 1`, а не `offset`

Коммит означает «с какой позиции продолжать», а не «что обработано последним».
Обработав запись с оффсетом 42, мы хотим при перезапуске начать с 43 —
иначе 42 обработается повторно.

### 12.3. `onPartitionsRevoked` против `onPartitionsLost`

`Revoked` — партиции отдаются штатно, в рамках ребалансировки. Они ещё ваши,
коммит валиден и обязателен.

`Lost` — партиции отобраны принудительно, консьюмер уже выпал из группы
(превышен `max.poll.interval.ms`, потеряна связь). Владелец сменился, и коммит
затрёт прогресс нового владельца более старым значением. Коммитить нельзя —
только очистить локальное состояние.

### 12.4. Как получить разные семантики порядком операций

**At-least-once:** обработать, потом закоммитить. Сбой между ними даёт дубль,
потеря невозможна.

**At-most-once:** закоммитить, потом обработать. Сбой между ними даёт потерю,
дубль невозможен.

**Exactly-once:** невозможно только порядком — нужны транзакции (этап 5) либо
идемпотентная обработка (этап 11).

Автокоммит не даёт ни одной из гарантий детерминированно: какая сработает,
зависит от тайминга срабатывания таймера.

### 12.5. Два консьюмера на один топик — в разных группах и в одной

**В разных группах** — оба получают **все** записи независимо. Это
publish-subscribe: у каждой группы свои оффсеты в `__consumer_offsets`.

**В одной группе с `subscribe`** — партиции делятся между ними, каждая запись
достаётся ровно одному. Это очередь с распределением нагрузки.

**В одной группе с `assign`** — координация не работает: `assign` не участвует
в группе. Если назначить обоим одну партицию, оба прочитают всё, а коммиты
будут затирать друг друга. Технически возможно, практически — ошибка.
