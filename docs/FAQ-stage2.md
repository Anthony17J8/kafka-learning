# Этап 2 — FAQ

Вопросы, возникшие в ходе практики. Базовые механизмы (acks, батчинг,
идемпотентность, компрессия) разобраны в `THEORY.md` — здесь только то,
что из него не выводится напрямую.

---

## 1. Если в одном потоке сначала несколько асинхронных отправок, а потом одна с `.get()` — попадёт ли последняя запись в общий батч?

Да, попадёт. `.get()` не влияет на записи, отправленные **до** него.

```java
send(r1); send(r2); send(r3); send(r4).get();
// r1-r4 накопились в буфере → один батч → один round-trip
```

К моменту `.get()` в аккумуляторе уже лежат все четыре. Если они идут в одну
партицию и помещаются в `batch.size`, Sender заберёт их одним батчем.

Разница с синхронным циклом:

```java
send(r1).get();  // буфер пуст после отправки
send(r2).get();  // только теперь r2 попадает в буфер
// 4 батча по одной записи, 4 round-trip'а
```

Блокировка **после каждой** записи гарантирует, что в момент следующего `send()`
буфер пуст — накопиться нечему структурно.

**Правило:** батчинг ломает не синхронность как таковая, а частота блокировок
относительно частоты отправок. Одна блокировка на 1000 записей почти не вредит,
одна на каждую — убивает батчинг полностью.

Отсюда рабочий production-паттерн «периодический барьер»: отправлять асинхронно,
но раз в N записей делать `.get()` — получаем батчинг и обратное давление
одновременно.

Оговорка про тайминг: при `linger.ms=0` Sender может забрать батч в любой момент,
поэтому попадание r1–r4 в один батч вероятно, но не гарантировано. При
`linger.ms > 0` поведение детерминированнее.

## 2. Почему при `acks=1` кластер медленнее одиночного брокера? Ведь в обоих случаях ждём ответа одного брокера

Протокол одинаков, но окружения нагружены по-разному. Четыре причины:

**Фолловеры создают фоновую нагрузку.** Лидер, помимо вашего продюсера,
обслуживает постоянные fetch-запросы двух фолловеров — отдельные соединения,
чтение из лога, обработка.

**Три контейнера делят ресурсы одной машины.** У вас не три сервера, а три
процесса на одном хосте: общий CPU, диск, сеть Docker. Каждый получает примерно
треть. На single весь хост принадлежит одному брокеру.

**Втрое больший объём записи на диск.** При RF=3 каждая запись физически
пишется трижды. `acks=1` не *ждёт* репликации, но репликация всё равно
происходит и конкурирует за диск.

**Записи размазаны по трём брокерам.** Топик из 3 партиций, лидеры на разных
нодах — продюсер держит три соединения и три потока запросов вместо одного.

Итого: интуиция «ждём одного брокера — значит одинаково» верна для протокола,
но не учитывает разницу в фоновой нагрузке.

## 3. Как сравнить степень сжатия, если все сценарии пишут в один топик подряд?

В таком виде — никак: данные накапливаются вперемешку, `kafka-log-dirs.sh`
покажет сумму всех прогонов. Три способа.

**Метрики продюсера (проще всего).** У `KafkaProducer` есть метрика
`compression-rate-avg` в группе `producer-metrics` — прямое отношение сжатого
размера к несжатому. Значение 1.0 = сжатия нет, 0.3 = сжато втрое.

```java
producer.flush();
// читаем producer.metrics() ДО закрытия
```

Значение приходит как `Object`, приводится через
`((Number) metric.metricValue()).doubleValue()`.

Плюс: ничего не надо создавать и чистить, добавляется колонка в таблицу.
Минус: измеряете то, что продюсер думает об отправленном, а не объём на диске.

**Отдельный топик на сценарий.** Создавать через `AdminClient` перед прогоном,
имена с UUID или удалять между прогонами. После — `kafka-log-dirs.sh --describe
--topic-list ...`. Учтите: покажет объём **всех реплик**, при RF=3 втрое больше
полезного (для сравнения между собой неважно, множитель одинаковый).

**Заглянуть в сегмент.** `kafka-dump-log.sh --files ...` покажет заголовки
батчей с полями `compresscodec` и `batchSize`. Заодно наглядно подтверждает,
что брокер хранит батч сжатым и не распаковывает его.

Ожидаемый результат для JSON из `OrderEvent`: сжатие в 3–5 раз. То есть
компрессия работает, просто в локальном окружении экономит бесплатный ресурс
(сеть между контейнерами) за счёт дефицитного (CPU).

## 4. В чём смысл задачи 5, если и так понятно, что `acks=all` надёжнее?

Смысл в том, чтобы увидеть **расхождение между «продюсер сказал, что записал»
и «в логе реально лежит»**.

При `acks=1` лидер отвечает «ок» сразу, не дожидаясь фолловеров. Callback
отработал без ошибки, счётчик вырос, приложение уверено в сохранности. Лидер
падает до репликации — запись исчезает. **Приложение об этом не узнает никогда:**
исключения не было, ошибки не было, логи чистые.

Отсюда конструкция эксперимента — два независимых числа:

- сколько продюсер считает подтверждённым (счётчик в callback);
- сколько реально записано (дельта `kafka-get-offsets.sh --time latest`).

При `acks=all` совпадают. При `acks=1` с падением лидера подтверждённых может
оказаться больше — разница и есть потеря.

Ценность в том, что сбой **тихий**. В продакшене мониторинг ничего не покажет,
пропажу обнаружат через недели при сверке отчётов. Задача 5 — возможность
увидеть тихий сбой в контролируемых условиях, зная, что искать.

Второй результат получается всегда, даже если потерю не поймать: замер
длительности провала при переизбрании лидера. Ваша собственная цифра вместо
общего утверждения «failover в KRaft быстрый».

## 5. Как проверить порядок записей в задаче 6, если консьюмеры ещё не проходили?

Через консольный консьюмер и `awk`, без Java.

Читаем в файл:

```bash
KAFKA_CONTAINER=kafka-1 BOOTSTRAP=kafka-1:19093 \
  ./scripts/kafka.sh kafka-console-consumer.sh \
    --topic ordering-test --from-beginning \
    --property print.offset=true \
    --timeout-ms 15000 > /tmp/ordering.txt
```

Проверяем монотонность:

```bash
awk -F'\t' '{
  v = $2 + 0
  if (NR > 1 && v < prev) { print "ИНВЕРСИЯ: после " prev " пришло " v " (" $1 ")"; bad++ }
  if (NR > 1 && v == prev) { print "ДУБЛЬ: " v " (" $1 ")"; dup++ }
  prev = v
}
END { print "прочитано: " NR ", инверсий: " bad+0 ", дублей: " dup+0 }' /tmp/ordering.txt
```

Два требования к продюсеру, чтобы это работало:

- значение записи — **голое число** (`String.valueOf(i)`), без префиксов вроде
  `value-123`: awk приводит строку к числу и на нечисловом получит 0;
- сериализатор строковый, не `IntegerSerializer` — последний пишет 4 байта
  big-endian, консольный консьюмер прочитает их как мусор.

Преимущество перед Java-верификатором: результат в файле, можно перечитывать
и анализировать без перезапуска эксперимента.

Топик пересоздавать перед каждым прогоном, иначе на стыке данных возникнет
ложная инверсия (после 49999 придёт 0 нового прогона).

## 6. Почему в одних командах порт 19093, а в других 19092?

Зависит от того, **откуда** выполняется команда.

| Порт | Листенер | Кто ходит |
|---|---|---|
| `19093` | `PLAINTEXT` | Брокеры между собой, контейнеры docker-сети |
| `9092` внутри → `19092` снаружи | `PLAINTEXT_HOST` | Клиенты с хост-машины |
| `9093` | `CONTROLLER` | Raft-кворум |

**`scripts/kafka.sh` работает через `docker exec`** — команда выполняется внутри
контейнера. Изнутри docker-сети `localhost:19092` бессмысленен (проброс портов
действует только для хоста), поэтому нужны внутренние адреса:

```bash
KAFKA_CONTAINER=kafka-1 BOOTSTRAP=kafka-1:19093 ./scripts/kafka.sh ...
```

**Java-код запускается на хосте** — для него работает проброшенный порт:

```bash
export BOOTSTRAP_SERVERS=localhost:19092,localhost:29092,localhost:39092
```

Правило: `docker exec` → `kafka-N:19093`; хост → `localhost:N9092`.

Внешние порты различаются (`19092`/`29092`/`39092`), потому что три контейнера
не могут занять один порт хоста. Внутренний `19093` одинаков у всех — внутри
сети у каждого свой IP, конфликта нет, различаются имена.

Механика, по которой клиент узнаёт адрес — `advertised.listeners`, см. теорию
этапа 0.

## 7. Почему при остановке двух брокеров команды зависают?

Потому что вы уронили **кворум контроллеров**, а не только брокеров.

В `three-broker.yml` каждая нода в combined-режиме (`process.roles=broker,controller`).
Останавливая два узла, вы убираете два голоса из трёх. Кворум требует
большинства — остался один голос, кворум распался.

`kafka-topics.sh --describe` запрашивает метаданные, а они живут в
`__cluster_metadata`, который обслуживают контроллеры. Без кворума лог не может
ни обновляться, ни отдавать актуальное состояние.

Оставшийся узел не отвечает отказом, а **ждёт**: с точки зрения протокола нет
разницы между «узел умер» и «узел недоступен из-за сетевого раздела». Объявить
себя лидером в одиночку он не может — при возвращении соседей получился бы
split-brain.

Это выбор консистентности над доступностью в чистом виде.

**Восстановление:** вернуть любой из двух (`docker start kafka-2`), кворум
соберётся за секунды. Проверка — `kafka-metadata-quorum.sh describe --status`,
смотреть на появление `LeaderId`.

**Для экспериментов:** останавливайте только один брокер за раз. Двух достаточно,
чтобы уронить кластер целиком, и тогда измеряется не failover, а полный отказ.

Практический аргумент за isolated-режим в продакшене: при вынесенных
контроллерах остановка двух **брокеров** не трогает кворум.

## 8. Что мешает параллельным запросам поменяться местами в штатном режиме?

TCP и последовательная обработка на брокере.

Продюсер держит **одно соединение** на брокера. Все запросы идут по нему
последовательно, TCP гарантирует порядок доставки байтов: A отправлен раньше B →
брокер **получит** A раньше B. Обгона не бывает.

Брокер обрабатывает запросы к одной партиции последовательно — записывает A,
потом B. Записать B раньше он не может, B ещё не пришёл.

`max.in.flight=5` означает «не жду ответа на A, чтобы отправить B». Это про
ожидание ответов, а не про независимые каналы.

### Тогда когда порядок ломается?

Только при **смене лидера**, и нужно совпадение шести условий:

1. Несколько запросов в полёте к одному лидеру (`max.in.flight > 1`).
2. `acks=1` — подтверждение без ожидания репликации.
3. Лидер падает, не отправив ответы (или ответы не дошли).
4. **Новый лидер имеет более позднюю запись B, но не имеет более ранней A.**
5. Продюсер повторяет неподтверждённые — A ложится после B.
6. Нет идемпотентности — брокер не проверяет sequence number и не замечает
   нарушения.

Пункт 4 — ключевой и самый узкий. Он возможен потому, что репликация идёт
батчами по расписанию фолловера: fetch-запрос забирает то, что есть на момент
запроса, и может прийти между записью A и B.

### Почему невозможно при `acks=all`

Подтверждение приходит только после того, как запись оказалась у всех реплик ISR.
Если продюсер не получил ответ на A — A либо есть у всех, либо нет ни у кого.
Репликация идёт строго по логу, B не может уехать раньше A. Асимметрия исключена.

Именно поэтому в задаче 6 нужен `acks=1` — вы намеренно открываете окно.

### Что на самом деле чинит идемпотентность

Не то, что ретрай опаздывает (это нормально), а то, что **никто не проверяет
порядковые номера**. С идемпотентностью брокер знает, что ждёт номер N; пришёл
N+1 — отклоняет, пока не придёт пропущенный.

## Общий вывод из вопросов 4 и 8

Два разных механизма — потеря записи при `acks=1` и переупорядочивание при
отключённой идемпотентности — дают один класс проблем: **данные повреждены,
приложение об этом не знает**. Оба невидимы для мониторинга, оба обнаруживаются
постфактум при сверке.

Оба закрыты правильными дефолтами в современной Kafka. Это и есть ответ на
вопрос, почему идемпотентность включили по умолчанию с версии 3.0: полагаться
на «у нас не воспроизводится» нельзя — окно существует по устройству протокола.
