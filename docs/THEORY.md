## 1. Модель хранения

### 1.1. Лог как базовая абстракция

Kafka хранит данные в виде **append-only лога** — упорядоченной последовательности
записей, в которую можно только дописывать в конец. Записи нельзя изменить,
нельзя вставить в середину, нельзя удалить по отдельности.

Три свойства следуют напрямую из этой модели:

**Чтение неразрушающее.** Consumer читает лог, не изменяя его. Сто консьюмеров
читают одни и те же байты. Брокер не хранит состояние «доставлено/не доставлено»
для каждой записи и каждого получателя — только позицию каждой группы.

**Запись последовательная.** Дописывание в конец файла — самый быстрый паттерн
работы с диском. На вращающемся диске это исключает перемещение головки; на SSD —
снижает write amplification. Пропускная способность последовательной записи
на порядок выше случайной.

**Состояние потребления вынесено к потребителю.** Позиция чтения — это просто
число, которым владеет консьюмер. Отсюда возможность перечитать историю, читать
с произвольной точки, иметь несколько независимых читателей.

### 1.2. Три уровня иерархии

```
Топик (логическое имя)
 └── Партиция (физический лог, единица параллелизма и порядка)
      └── Реплика (копия партиции на конкретном брокере)
           └── Сегмент (файл на диске)
```

**Топик** не существует физически. Это имя, под которым сгруппирован набор
партиций. Все операции с данными идут на уровне партиции.

**Партиция** — независимый лог со своей нумерацией записей. Партиции одного топика
никак не связаны между собой: у них разные лидеры, разные оффсеты, разный объём.

**Реплика** — полная копия партиции на отдельном брокере. Число реплик задаётся
`replication.factor`. Одна из реплик в каждый момент времени является лидером.

**Сегмент** — файл фиксированного размера, из которых складывается лог реплики.

### 1.3. Структура записи

Каждая запись (record) содержит:

| Поле | Назначение |
|---|---|
| Key | Ключ, определяет партицию и участвует в компакции. Может быть `null` |
| Value | Полезная нагрузка. `null` означает tombstone в compacted-топике |
| Timestamp | Время создания или время записи (см. `message.timestamp.type`) |
| Headers | Произвольные пары ключ-значение для метаданных |
| Offset delta | Смещение относительно базового оффсета батча |

Настройка `message.timestamp.type` принимает два значения:

- `CreateTime` (по умолчанию) — timestamp ставит продюсер. Это event time,
  на нём строится оконная логика Kafka Streams.
- `LogAppendTime` — timestamp перезаписывает брокер при записи. Это ingestion time.

Выбор влияет на `.timeindex` и, соответственно, на результат `offsetsForTimes()`.

### 1.4. Record batch — реальная единица хранения

Записи никогда не хранятся и не передаются поодиночке. Продюсер собирает их
в **record batch**, и дальше батч живёт как единое целое от продюсера до диска
и обратно до консьюмера.

Заголовок батча (формат v2) содержит:

| Поле | Зачем |
|---|---|
| `baseOffset` | Оффсет первой записи; остальные хранят дельту |
| `partitionLeaderEpoch` | Эпоха лидера, см. раздел 5.6 |
| `crc` | Контрольная сумма всего батча |
| `attributes` | Тип компрессии, тип timestamp, флаг транзакции |
| `lastOffsetDelta` | Число записей в батче минус один |
| `baseTimestamp`, `maxTimestamp` | Границы времени в батче |
| `producerId`, `producerEpoch`, `baseSequence` | Идемпотентность и транзакции |

Практические следствия, о которых часто забывают:

**Компрессия применяется к батчу целиком.** Сжимается не каждое сообщение,
а весь блок сразу — поэтому эффективность растёт с размером батча. Батч из одного
сообщения сжимать почти бессмысленно.

**Брокер не распаковывает батч.** При совпадении формата и типа компрессии батч
записывается на диск как есть и отдаётся консьюмеру как есть. Именно это делает
возможным zero-copy (раздел 4.6). Распаковка происходит на стороне консьюмера.

**Оффсеты хранятся дельтами.** В батче лежит один полный оффсет и набор коротких
приращений — экономия места.

**Retention работает по батчам.** Kafka не может удалить одну запись из батча.
Минимальная единица удаления — сегмент, состоящий из батчей.

## 2. Партиционирование

### 2.1. Зачем нужны партиции

Одна партиция — это один лог на одном брокере. Её пропускная способность
ограничена диском и сетью этого брокера. Разделив топик на N партиций
и распределив их по кластеру, вы получаете:

- **Горизонтальное масштабирование записи** — продюсеры пишут в разные партиции параллельно
- **Горизонтальное масштабирование чтения** — до N консьюмеров в группе работают одновременно
- **Распределение объёма** — данные топика не обязаны помещаться на один диск

Цена — потеря глобального порядка.

### 2.2. Как выбирается партиция

Логика находится на стороне **продюсера**, не брокера.

**Если ключ задан:**

```
partition = Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions
```

Хеш murmur2 детерминирован и не зависит от языка клиента, поэтому Java-продюсер
и Python-продюсер положат одинаковый ключ в одну партицию.

**Если ключ равен `null`:** используется sticky-стратегия (KIP-480, уточнена
в KIP-794). Продюсер выбирает одну партицию и пишет в неё, пока не наберётся
батч, затем переключается на следующую. Это заметно плотнее набивает батчи,
чем round-robin по каждому сообщению.

**Кастомный партиционер** подключается через `partitioner.class`. Реализует
интерфейс `Partitioner` — см. заготовку `CustomPartitioner` в модуле `02-producers`.

### 2.3. Что именно гарантируется по порядку

Гарантия ровно одна: **записи внутри одной партиции консьюмер видит в том же
порядке, в котором они были записаны**.

Из этого не следует:

- Порядок между партициями одного топика — не гарантирован
- Порядок между топиками — не гарантирован
- Порядок при отправке одного ключа несколькими продюсерами — определяется тем,
  кто раньше дошёл до брокера, а не тем, кто раньше вызвал `send()`

Порядок внутри партиции может нарушиться и в одном случае на стороне продюсера:
при `max.in.flight.requests.per.connection > 1` без идемпотентности повторная
отправка упавшего запроса может обогнать следующий за ним. Идемпотентный продюсер
(включён по умолчанию) этот случай закрывает: брокер отслеживает последовательные
номера и восстанавливает порядок.

### 2.4. Почему число партиций нельзя уменьшить

Формула из 2.2 привязывает ключ к партиции через `% numPartitions`. При изменении
знаменателя отображение меняется для большинства ключей.

**При увеличении** старые записи остаются в прежних партициях, новые с тем же
ключом уходят в другую. Порядок по ключу разрывается: события заказа №42 будут
частично в партиции 3, частично в партиции 7, и относительный порядок между ними
не определён. Kafka это разрешает, но последствия на вашей совести.

**При уменьшении** дополнительно возникает вопрос, куда девать данные удаляемых
партиций. Любое решение ломает либо оффсеты (они уникальны в пределах партиции
и при слиянии конфликтуют), либо порядок, либо и то и другое. Поэтому операция
не поддерживается вовсе.

Единственный корректный способ «уменьшить» — создать новый топик с нужным числом
партиций и перелить данные.

### 2.5. Как выбрать число партиций

Отправная точка — целевая пропускная способность:

```
N = max(целевой_throughput / throughput_одной_партиции_на_запись,
        целевой_throughput / throughput_одной_партиции_на_чтение)
```

Практические ограничители:

**Число партиций ≥ желаемого числа консьюмеров в группе.** Партиций меньше,
чем консьюмеров — лишние консьюмеры простаивают. Это жёсткий потолок параллелизма.

**Больше партиций — больше накладных расходов.** Каждая партиция это открытые
файловые дескрипторы, отдельный буфер в памяти продюсера, отдельная запись
в метаданных, отдельная единица при ребалансировке. Тысячи партиций на брокер
заметно увеличивают время восстановления после перезапуска.

**Больше партиций — выше end-to-end latency.** Запись становится видимой
консьюмеру только после репликации; при большом числе партиций фоновая
репликационная нагрузка растёт.

**Заложите запас.** Увеличить можно, уменьшить нельзя. Типичный подход —
взять расчётное значение и умножить на 2–3.

Ориентир для современных кластеров: до нескольких тысяч партиций на брокер
и до сотен тысяч на кластер. С переходом на KRaft верхняя граница выросла
на порядок по сравнению с эпохой ZooKeeper.

## 3. Оффсеты и границы видимости

### 3.1. Свойства оффсета

Оффсет — порядковый номер записи внутри партиции.

- Начинается с нуля
- Монотонно возрастает
- Никогда не переиспользуется, даже после удаления данных
- Уникален только в пределах партиции

Полный адрес записи — тройка `(topic, partition, offset)`.

После компакции в нумерации появляются **разрывы**: оффсеты 0, 1, 2 могут
исчезнуть, а 3 остаться. Консьюмер, читающий последовательно, просто перескочит
отсутствующие номера — это нормально и не является ошибкой.

### 3.2. Четыре границы в логе

В любой момент в партиции определены несколько важных позиций:

| Граница | Что означает | Кто видит |
|---|---|---|
| **Log Start Offset** | Первый доступный оффсет (растёт при удалении сегментов) | Все |
| **LEO** (Log End Offset) | Оффсет, следующий за последней записью реплики | Внутреннее |
| **HW** (High Watermark) | Минимальный LEO среди реплик в ISR | Граница видимости для консьюмера |
| **LSO** (Last Stable Offset) | `min(HW, оффсет первой открытой транзакции)` | Граница для `read_committed` |

Обычный консьюмер (`isolation.level=read_uncommitted`, по умолчанию) читает
до **HW**. Консьюмер с `read_committed` — до **LSO**. Разница проявляется только
при использовании транзакций (этап 5).

Именно `Log Start Offset` объясняет ошибку `OffsetOutOfRangeException`:
консьюмер запросил оффсет, который уже удалён по retention. Поведение в этом
случае определяется настройкой `auto.offset.reset` (`earliest` / `latest` / `none`).

### 3.3. Где хранятся оффсеты консьюмеров

Во внутреннем топике `__consumer_offsets` — обычном compacted-топике
с 50 партициями по умолчанию.

- **Ключ:** `(group.id, topic, partition)`
- **Значение:** оффсет, метаданные, timestamp коммита

Партиция для группы выбирается как `hash(group.id) % 50`. Лидер этой партиции
становится **group coordinator** для данной группы — он же обслуживает
ребалансировки.

Компакция здесь работает ровно по назначению: хранится только последний
закоммиченный оффсет каждой группы, история коммитов не нужна.

## 4. Физическое хранение на диске

### 4.1. Каталог партиции

Каждая реплика — это каталог вида `<topic>-<partition>` внутри `log.dirs`:

```
/var/lib/kafka/data/orders-0/
├── 00000000000000000000.log          данные (record batches)
├── 00000000000000000000.index        оффсет → байтовая позиция
├── 00000000000000000000.timeindex    timestamp → оффсет
├── 00000000000000524288.log          следующий сегмент
├── 00000000000000524288.index
├── 00000000000000524288.timeindex
├── 00000000000000524288.snapshot     состояние идемпотентных продюсеров
└── leader-epoch-checkpoint           история смен лидера
```

Имя файла — оффсет первой записи в сегменте, дополненный нулями до 20 знаков.

### 4.2. Сегменты и их ротация

Запись всегда идёт в последний, **активный** сегмент. Он закрывается и создаётся
новый, когда выполняется любое из условий:

| Настройка | По умолчанию | Условие |
|---|---|---|
| `segment.bytes` | 1 ГБ | Размер активного сегмента достиг порога |
| `segment.ms` | 7 суток | Активный сегмент существует дольше порога |
| `index.interval.bytes` косвенно | — | Индекс переполнился (`segment.index.bytes`, 10 МБ) |

**Активный сегмент неприкосновенен.** Ни retention, ни компакция его не трогают.
Это единственная причина большинства недоумений вида «поставил retention.ms=60000,
а данные не удаляются» — сегмент просто ещё не закрылся.

### 4.3. Индекс по оффсетам (`.index`)

**Разрежённый** индекс: запись добавляется не для каждого сообщения, а примерно
каждые `index.interval.bytes` байт (по умолчанию 4096).

Формат записи — пара из 4-байтового относительного оффсета и 4-байтовой позиции
в файле. Восемь байт на запись.

Поиск оффсета работает в два шага: бинарный поиск по индексу находит ближайшую
предшествующую позицию, дальше идёт последовательное сканирование `.log`
до нужной записи. Разрежённость — компромисс: индекс маленький и целиком
помещается в память, цена — небольшое линейное дочитывание.

### 4.4. Индекс по времени (`.timeindex`)

Пары «timestamp → относительный оффсет», тоже разрежённые. На нём построены:

- `consumer.offsetsForTimes()` — см. `SeekingConsumer` в модуле `03-consumers`
- Retention по времени — определение возраста сегмента
- `kafka-consumer-groups.sh --reset-offsets --to-datetime`

Важно: при `message.timestamp.type=CreateTime` временной индекс отражает время,
проставленное продюсером. Если продюсер прислал записи с «кривыми» timestamp
(например, при переигрывании старых данных), retention может удалить их сразу же.

### 4.5. Служебные файлы

**`.snapshot`** — периодические снимки состояния идемпотентных продюсеров
(`producerId` → последний sequence number). Нужны, чтобы после перезапуска брокера
не перечитывать весь лог для восстановления дедупликации.

**`leader-epoch-checkpoint`** — история пар `(эпоха, начальный оффсет)`.
Механизм разбирается в разделе 5.6.

### 4.6. Page cache и zero-copy

Kafka сознательно **не строит собственный кеш данных** в куче JVM. Вместо этого
она полагается на page cache операционной системы.

Логика такая. Данные пишутся через обычный `write()` в page cache; ядро сбрасывает
их на диск асинхронно. Консьюмер, читающий недавние записи, попадает в тот же
page cache и до диска вообще не доходит. Типичный сценарий «консьюмер читает
с хвоста» обслуживается полностью из памяти.

Преимущества перед кешем в куче:

- Нет давления на GC от гигабайтов закешированных данных
- Кеш переживает перезапуск брокера (данные остаются в page cache ОС)
- Нет дублирования: данные не лежат одновременно в page cache и в куче

Отсюда практическое правило по памяти: **давайте JVM небольшую кучу (6–8 ГБ)
и оставляйте остальное системе под page cache.** Раздутая куча ухудшает
производительность Kafka, а не улучшает.

**Zero-copy.** При отдаче данных консьюмеру Kafka вызывает `sendfile()`: ядро
копирует байты из page cache напрямую в сетевой сокет, не поднимая их
в пользовательское пространство и не проводя через JVM.

Условие работы zero-copy — брокеру не нужно **трогать** данные. Именно поэтому
брокер не распаковывает батчи. Но zero-copy отключается, если:

- Включено шифрование TLS (данные нужно зашифровать, а значит прочитать)
- Требуется конвертация формата между версиями протокола

Первое стоит держать в голове на этапе 10: включение TLS даёт реальную просадку
пропускной способности, и это не миф, а следствие потери zero-copy.

### 4.7. Почему последовательный доступ так важен

Последовательная запись на диск даёт сотни мегабайт в секунду даже на HDD,
случайная — единицы. Kafka выстроена так, чтобы весь дисковый ввод-вывод был
последовательным: запись всегда в конец активного сегмента, чтение всегда
вперёд по логу.

Это же объясняет, почему Kafka комфортно работает на дешёвых дисках и почему
объём данных на брокере может многократно превышать объём его памяти
без деградации производительности.

## 5. Репликация

### 5.1. Лидер и фолловеры

Из `replication.factor` реплик одна назначается **лидером**, остальные —
**фолловерами**.

- Весь клиентский трафик (запись и чтение) обслуживает лидер
- Фолловеры вычитывают данные у лидера обычным `Fetch`-запросом — тем же самым,
  каким пользуются консьюмеры
- Фолловеры не обслуживают клиентов и существуют исключительно ради отказоустойчивости

Реплики одной партиции всегда лежат на **разных брокерах** — иначе смысл теряется.

> Начиная с KIP-392 консьюмер может читать с ближайшей реплики
> (`client.rack` + `replica.selector.class`) ради экономии межзонального трафика.
> Это оптимизация для облачных развёртываний; базовая модель остаётся
> «всё через лидера».

### 5.2. ISR — In-Sync Replicas

**ISR** — подмножество реплик, которые считаются поспевающими за лидером.
Лидер всегда входит в ISR.

Критерий исключения: реплика не отправляла `Fetch`-запрос, догоняющий LEO лидера,
дольше `replica.lag.time.max.ms` (по умолчанию **30 секунд**).

Обратите внимание, что критерий **временной**, а не по числу отставших записей.
Раньше существовала настройка `replica.lag.max.messages`, но она была удалена:
при всплеске трафика по ней из ISR вылетали абсолютно здоровые реплики.

Изменения состава ISR фиксируются в метаданных кластера контроллером.
Метрики `IsrShrinksPerSec` и `IsrExpandsPerSec` — один из первых индикаторов
проблем с сетью или дисками.

### 5.3. Как продвигается high-watermark

Механика в деталях:

1. Продюсер записывает батч. Лидер дописывает его в свой лог, его LEO растёт.
2. Каждый фолловер шлёт `Fetch`-запрос, указывая **свой текущий LEO**.
3. Лидер по этим значениям знает LEO всех реплик и вычисляет
   `HW = min(LEO по всем репликам в ISR)`.
4. В ответе на `Fetch` лидер сообщает фолловерам новое значение HW.

Отсюда важное следствие: **фолловер узнаёт о продвижении HW на один раунд позже**,
чем оно фактически произошло. Это нормально и учтено в протоколе.

Консьюмер видит записи только до HW. Записи выше HW физически на лидере есть,
но отдавать их нельзя: при падении лидера они могут исчезнуть, а консьюмер
их уже обработал бы.

### 5.4. `acks` и `min.insync.replicas`

Настройка `acks` живёт на **продюсере** и определяет, чего он ждёт:

| `acks` | Продюсер ждёт | Риск |
|---|---|---|
| `0` | Ничего, отправил и забыл | Потеря при любом сбое; несовместимо с идемпотентностью |
| `1` | Запись в лог лидера | Потеря, если лидер упадёт до репликации |
| `all` (`-1`) | Подтверждение от всех реплик **в ISR** | Минимальный |

Ключевая тонкость: `acks=all` ждёт подтверждения от текущего ISR, а не от всех
реплик вообще. Если ISR схлопнулся до одного лидера, то `all` означает
«подтверждено одним узлом» — то есть ровно то же, что `acks=1`.

Настройка `min.insync.replicas` живёт на **брокере/топике** и закрывает эту дыру.
Она задаёт минимальный размер ISR, при котором запись вообще принимается.
Если реплик в ISR меньше, лидер отвечает `NotEnoughReplicasException`.

**Работает только в паре с `acks=all`.** При `acks=1` настройка игнорируется.

Матрица для RF=3:

| `min.insync.replicas` | Живых реплик | Запись `acks=all` | Чтение |
|---|---|---|---|
| 2 | 3 | Работает | Работает |
| 2 | 2 | Работает, без запаса | Работает |
| 2 | 1 | **Отвергается** | Работает |
| 1 | 1 | Работает, но данные на одном узле | Работает |
| 3 | 2 | **Отвергается** | Работает |

Стандартная продакшн-конфигурация для важных данных — **RF=3,
`min.insync.replicas=2`, `acks=all`**. Она переживает отказ одного брокера
без остановки записи и не допускает подтверждения записи, существующей
в единственном экземпляре.

Значение `min.insync.replicas=3` при RF=3 — распространённая ошибка: любой
перезапуск брокера полностью останавливает запись.

### 5.5. Что происходит при отказе брокера

1. Контроллер обнаруживает потерю связи с брокером (по истечении сессии).
2. Для каждой партиции, где упавший брокер был лидером, контроллер выбирает
   нового лидера из ISR.
3. Решение записывается в лог метаданных и распространяется по кластеру.
4. Клиенты получают ошибку `NOT_LEADER_OR_FOLLOWER`, обновляют метаданные
   и переподключаются к новому лидеру. Для приложения это выглядит как краткая
   задержка, а не как сбой — при условии, что ретраи настроены.

Партиции, где упавший брокер был фолловером, продолжают работать, но их ISR
сокращается.

### 5.6. Leader epoch — защита от расхождения логов

Проблема, которую решает механизм (KIP-101). После смены лидера у бывшего лидера
могли остаться записи выше HW, которых нет у нового лидера. Раньше вернувшаяся
реплика усекала свой лог до HW — и в редких сценариях это приводило либо к потере
подтверждённых данных, либо к расхождению содержимого реплик.

Решение: каждой «эпохе» лидерства присваивается монотонно растущий номер.
При каждой смене лидера эпоха увеличивается. История пар
`(эпоха, начальный оффсет)` хранится в файле `leader-epoch-checkpoint`,
а номер эпохи пишется в заголовок каждого record batch.

Вернувшаяся реплика теперь спрашивает у лидера не «какой у тебя HW», а «какой
последний оффсет в эпохе N» — и усекает лог ровно по точке фактического
расхождения. Корректность больше не зависит от того, успел ли распространиться HW.

Знать этот механизм наизусть не требуется, но он объясняет, зачем в заголовке
батча лежит `partitionLeaderEpoch` и что за файл `leader-epoch-checkpoint`
в каталоге партиции.

## 6. Выборы лидера

### 6.1. Preferred leader

При создании топика Kafka распределяет реплики по брокерам и запоминает порядок.
**Первая реплика в списке** называется preferred leader — предпочтительным лидером.

```
Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
                                     ↑            ↑
                              текущий лидер   preferred = 1
```

Смысл в равномерности: при создании топика preferred-лидеры раскладываются
по брокерам равномерно. После серии отказов и восстановлений лидерство
может перекоситься — все партиции окажутся на одном-двух брокерах.

Настройка `auto.leader.rebalance.enable` (по умолчанию `true`) заставляет
контроллер периодически возвращать лидерство preferred-репликам. Проверка
идёт каждые `leader.imbalance.check.interval.seconds` (300), срабатывает
при перекосе больше `leader.imbalance.per.broker.percentage` (10%).

Вручную:

```bash
kafka-leader-election.sh --bootstrap-server ... --election-type PREFERRED --all-topic-partitions
```

### 6.2. Unclean leader election

Настройка `unclean.leader.election.enable`, по умолчанию **`false`**.

Сценарий: все реплики из ISR недоступны, но живёт реплика, давно выпавшая
из ISR и отставшая на тысячи записей.

- **`false`** — партиция становится **недоступной** до возвращения одной
  из реплик ISR. Данные не теряются, но и работать нельзя.
- **`true`** — отставшая реплика становится лидером. Партиция оживает,
  но записи между её LEO и прежним HW **теряются безвозвратно**.

Это выбор между консистентностью и доступностью в чистом виде — та самая
CAP-дилемма, но в конкретной формулировке. По умолчанию Kafka выбирает
консистентность.

Включать `true` осмысленно для данных, где свежесть важнее полноты: метрики,
логи, телеметрия. Для финансовых транзакций — никогда.

### 6.3. Роль контроллера

Активный контроллер (раздел про KRaft из этапа 0) отвечает за:

- Отслеживание живости брокеров
- Назначение лидеров партиций
- Изменение состава ISR
- Обработку создания/удаления топиков, изменения конфигураций
- Реассайн реплик

Все эти решения записываются в лог метаданных `__cluster_metadata`, откуда
их вычитывают брокеры.

## 7. Retention — удаление по времени и объёму

### 7.1. Настройки

Политика `cleanup.policy=delete` (по умолчанию).

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `retention.ms` | 604800000 (7 суток) | Максимальный возраст данных |
| `retention.bytes` | -1 (без ограничения) | Максимальный размер **партиции** |
| `segment.ms` | 604800000 (7 суток) | Принудительная ротация сегмента |
| `segment.bytes` | 1073741824 (1 ГБ) | Размер сегмента |
| `file.delete.delay.ms` | 60000 | Задержка между переименованием и удалением |
| `log.retention.check.interval.ms` | 300000 (брокерная) | Как часто проверять |

Условия `retention.ms` и `retention.bytes` работают **независимо**: сегмент
удаляется, если сработало любое из них.

Критично: `retention.bytes` задаётся **на партицию**, а не на топик. Топик
из 12 партиций с `retention.bytes=1GB` займёт до 12 ГБ на реплику,
то есть до 36 ГБ при RF=3.

### 7.2. Как происходит удаление

1. Фоновый поток раз в `log.retention.check.interval.ms` обходит закрытые сегменты.
2. Сегмент считается устаревшим, если максимальный timestamp в нём старше
   `retention.ms`, либо если суммарный размер партиции превышает `retention.bytes`.
3. Устаревший сегмент **переименовывается** с суффиксом `.deleted`,
   `Log Start Offset` сдвигается вперёд.
4. Через `file.delete.delay.ms` файл физически удаляется.

Двухфазность нужна, чтобы не выдернуть файл из-под консьюмера, который в этот
момент его читает.

### 7.3. Почему данные не удаляются, когда ожидалось

Три причины по частоте:

**Активный сегмент не удаляется никогда.** Пока сегмент не закрыт по
`segment.bytes` или `segment.ms`, его содержимое живёт вечно. На тестовом топике
с малым трафиком сегмент закроется только через `segment.ms` — по умолчанию
через неделю.

Для экспериментов задавайте оба параметра:

```bash
--config retention.ms=60000 --config segment.ms=10000
```

**Проверка идёт раз в 5 минут.** Удаление не мгновенно даже после закрытия сегмента.

**Timestamp записей отличается от ожидаемого.** При `CreateTime` возраст
считается по времени, проставленному продюсером. При переигрывании исторических
данных сегменты могут быть удалены сразу после закрытия.

## 8. Compaction — сжатие по ключу

### 8.1. Модель

Политика `cleanup.policy=compact`. Kafka гарантирует, что для каждого ключа
в логе **сохранится хотя бы последнее записанное значение**.

Топик перестаёт быть потоком событий и становится **реплицируемой таблицей**:
размер определяется числом уникальных ключей, а не объёмом трафика.

Обязательное условие: **у всех записей должен быть ключ**. Запись с `null`-ключом
в compacted-топике не может быть обработана компактором.

### 8.2. Структура лога при компакции

Лог делится на две части:

```
[         tail (compacted)         ][      head (dirty)      ][active]
 уникальные ключи, уже обработаны    ещё не обработано        пишется
```

**Head** («грязная» часть) — сегменты, записанные после последнего прохода
компактора. Здесь ключи могут дублироваться.

**Tail** — уже обработанная часть, где каждый ключ встречается не более одного раза.

Фоновые потоки log cleaner (`log.cleaner.threads`, по умолчанию 1) обрабатывают
head, строят карту «ключ → последний оффсет» и переписывают сегменты, выбрасывая
устаревшие версии.

### 8.3. Когда запускается компакция

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `min.cleanable.dirty.ratio` | 0.5 | Доля head от общего размера, при которой запускается чистка |
| `min.compaction.lag.ms` | 0 | Минимальный возраст записи до попадания под компакцию |
| `max.compaction.lag.ms` | ~∞ | Максимальная задержка до обязательной компакции |
| `delete.retention.ms` | 86400000 (24 ч) | Сколько живёт tombstone после компакции |
| `segment.ms` | 7 суток | Ротация — компактор работает только с закрытыми сегментами |

**`min.cleanable.dirty.ratio` — главная причина «компакция не работает».**
По умолчанию 0.5: пока половина лога не станет «грязной», чистка не запустится.
На маленьком тестовом топике этого не произойдёт никогда.

Для экспериментов:

```bash
--config cleanup.policy=compact \
--config min.cleanable.dirty.ratio=0.01 \
--config segment.ms=10000 \
--config delete.retention.ms=1000
```

`max.compaction.lag.ms` появилась для регуляторных требований (GDPR): она
гарантирует, что удаление ключа будет применено не позже заданного срока,
независимо от dirty ratio.

### 8.4. Tombstone

Чтобы удалить ключ из compacted-топика, пишут запись с этим ключом
и **значением `null`** — tombstone («надгробие»).

Логика жизненного цикла:

1. Tombstone записывается в лог как обычная запись.
2. При компакции она вытесняет все предыдущие версии ключа.
3. Сама tombstone сохраняется ещё `delete.retention.ms` (по умолчанию сутки).
4. По истечении срока удаляется и она — ключ исчезает полностью.

Отсрочка на шаге 3 существует ради консьюмеров. Отставший консьюмер должен
успеть увидеть факт удаления. Исчезни tombstone сразу — консьюмер, читающий лог
с начала, никогда бы не узнал, что ключ был удалён, и сохранил бы у себя
устаревшее значение.

Отсюда практическое требование: **консьюмер compacted-топика обязан корректно
обрабатывать `null`-значение** как сигнал удаления, а не падать на нём.

### 8.5. Что консьюмер увидит в compacted-топике

Гарантии:

- Для каждого ключа будет прочитано его последнее значение
- Порядок записей сохраняется (относительный порядок уцелевших записей
  тот же, что при записи)
- Оффсеты не меняются, но появляются разрывы

Чего гарантий **нет**:

- Что промежуточные версии ключа не будут прочитаны — компакция асинхронна,
  консьюмер может прочитать head до его обработки
- Что консьюмер, читающий «с хвоста», увидит все ключи — он увидит только
  те, что записывались после его подключения

Второе — причина, по которой Kafka Streams при построении `KTable` перечитывает
топик с начала.

### 8.6. Совмещение политик

```properties
cleanup.policy=compact,delete
```

Работают обе: сохраняются последние версии ключей, но всё старше `retention.ms`
удаляется независимо от того, последняя это версия ключа или нет.

Так настроен `__consumer_offsets`: актуальные оффсеты нужны, но данные групп,
не появлявшихся месяцами, хранить бессмысленно.

### 8.7. Как выбрать политику

| Признак | `delete` | `compact` |
|---|---|---|
| Природа данных | Поток событий | Текущее состояние |
| Ценность записи | Каждая самоценна | Ценна только последняя по ключу |
| Ключ | Опционален | Обязателен |
| Рост объёма | По трафику | По числу уникальных ключей |
| Примеры | Заказы, клики, логи, метрики | Профили, справочники, цены, конфигурация |
| В нашем проекте | `orders`, `metrics` | `users` |

## 11. Развёрнутые ответы на контрольные вопросы

### 11.1. Почему число партиций легко увеличить, но нельзя уменьшить?

Партиция для ключа вычисляется как `hash(key) % numPartitions`. Изменение
знаменателя меняет отображение для большинства ключей.

При увеличении Kafka не перекладывает существующие записи — это было бы
неподъёмной операцией и всё равно сломало бы оффсеты. Старые записи остаются
на местах, новые с тем же ключом уходят в другую партицию. Порядок по ключу
разрывается необратимо, и события одной сущности оказываются размазаны
по двум партициям без определённого взаимного порядка.

Уменьшение добавляет неразрешимую проблему: данные удаляемых партиций некуда
деть. Слить их в оставшиеся нельзя — оффсеты уникальны только внутри партиции
и при слиянии конфликтуют. Удалить — потеря данных. Поэтому операция
не поддерживается в принципе.

Корректный путь при необходимости уменьшения — новый топик и перелив данных.

### 11.2. В чём разница между retention и compaction? Можно ли включить оба?

`retention` (`cleanup.policy=delete`) удаляет данные по **возрасту** или
**суммарному объёму**, не глядя на содержимое. Модель — поток событий
с ограниченным окном хранения.

`compaction` (`cleanup.policy=compact`) удаляет **устаревшие версии ключей**,
сохраняя последнюю. Возраст роли не играет: запись годичной давности останется,
если это последнее значение своего ключа. Модель — реплицируемая таблица.

Совмещаются через `cleanup.policy=compact,delete`. Тогда сохраняются последние
версии ключей, но всё старше `retention.ms` удаляется независимо от версии.
Так устроен `__consumer_offsets`.

### 11.3. Что такое high-watermark и почему консьюмер не видит записи выше него?

High-watermark — минимальный LEO среди реплик в ISR, то есть оффсет, до которого
данные подтверждены **всеми** синхронными репликами.

Записи выше HW физически лежат на лидере, но ещё не реплицированы. Если лидер
упадёт до их репликации, новый лидер будет выбран из ISR — а у него этих записей
нет. Они исчезнут.

Отдай Kafka такие записи консьюмеру — и возникла бы ситуация, когда консьюмер
обработал событие, которого в кластере больше не существует. HW делает эту
ситуацию невозможной: видимое консьюмеру гарантированно переживёт отказ лидера.

### 11.4. RF=3, `min.insync.replicas=2`: что при падении двух брокеров?

ISR сократится до одной реплики (лидера).

- **Запись с `acks=all`** будет отвергаться с `NotEnoughReplicasException` —
  размер ISR (1) меньше требуемого минимума (2).
- **Запись с `acks=1` или `acks=0`** продолжит работать, но данные окажутся
  в единственном экземпляре.
- **Чтение** продолжит работать: лидер жив и отдаёт данные до HW.

Партиция становится доступной только на чтение. Это осознанный выбор:
отказать в записи безопаснее, чем подтвердить данные, которые исчезнут
вместе с последним живым узлом.

При возвращении одного брокера его реплика догонит лидера, войдёт в ISR,
и запись возобновится автоматически.

### 11.5. Зачем нужен tombstone в compacted-топике?

Компакция сохраняет последнее значение каждого ключа. Выразить в этой модели
«ключа больше нет» невозможно — «отсутствие последнего значения» не является
записью и не может быть записано.

Tombstone (запись с `null`-значением) решает задачу: она сама становится
последней версией ключа, вытесняет все предыдущие, а затем через
`delete.retention.ms` удаляется и сама, унося ключ полностью.

Отсрочка удаления самой tombstone нужна отставшим консьюмерам: они должны
успеть увидеть факт удаления. Иначе консьюмер, читающий лог с начала после
исчезновения tombstone, никогда не узнал бы об удалении и сохранил бы у себя
устаревшее значение.

## 12. Диагностические команды

```bash
# --- Метаданные топика: лидеры, реплики, ISR ---
kafka-topics.sh --bootstrap-server $BOOT --describe --topic orders

# Только проблемные партиции
kafka-topics.sh --bootstrap-server $BOOT --describe --under-replicated-partitions
kafka-topics.sh --bootstrap-server $BOOT --describe --unavailable-partitions
kafka-topics.sh --bootstrap-server $BOOT --describe --at-min-isr-partitions

# --- Границы лога ---
# Log Start Offset (начало) и LEO (конец) по каждой партиции
kafka-get-offsets.sh --bootstrap-server $BOOT --topic orders --time earliest
kafka-get-offsets.sh --bootstrap-server $BOOT --topic orders --time latest
# Оффсет по времени
kafka-get-offsets.sh --bootstrap-server $BOOT --topic orders --time 1700000000000

# --- Размер на диске ---
kafka-log-dirs.sh --bootstrap-server $BOOT --describe --topic-list orders

# --- Конфигурация топика ---
kafka-configs.sh --bootstrap-server $BOOT --entity-type topics --entity-name orders --describe

# --- Заглянуть внутрь сегмента (запускать внутри контейнера) ---
kafka-dump-log.sh --files /var/lib/kafka/data/orders-0/00000000000000000000.log --print-data-log
# Только заголовки батчей, без содержимого
kafka-dump-log.sh --files /var/lib/kafka/data/orders-0/00000000000000000000.log
# Разбор индекса
kafka-dump-log.sh --files /var/lib/kafka/data/orders-0/00000000000000000000.index

# --- Файлы партиции ---
ls -la /var/lib/kafka/data/orders-0/
cat /var/lib/kafka/data/orders-0/leader-epoch-checkpoint
```

Утилита `kafka-dump-log.sh` — самая недооценённая в дистрибутиве. Она показывает
реальную структуру батчей: базовые оффсеты, эпохи лидера, тип компрессии,
producerId. Один запуск на живом топике объясняет разделы 1.4 и 4 нагляднее
любого текста.
