## 1. Конвейер отправки

`producer.send()` не отправляет запись на брокер. Он проводит её через несколько
стадий и возвращает управление, а реальную отправку делает отдельный поток.

```
Ваш поток:
  send(record)
    → сериализация (key, value → байты)
    → партиционер (выбор партиции)
    → запись кладётся в буфер аккумулятора
    → возврат Future, управление вернулось вам

Фоновый поток Sender (io-thread):
    → берёт готовые батчи из аккумулятора
    → группирует по брокерам-лидерам
    → отправляет, ждёт ответ согласно acks
    → выполняет callback / завершает Future
```

Ключевое следствие: **между `send()` и фактической записью проходит время**,
и почти все настройки продюсера регулируют одну из стадий этого конвейера.

Два потока:
- **Главный поток** (ваш код) — сериализует, партиционирует, кладёт в буфер.
- **Sender-поток** — единственный, кто общается с брокерами по сети.

Поэтому `send()` быстрый: он не ждёт сети. Ожидание сети берёт на себя Sender.

## 2. Сериализация

Kafka хранит байты и ничего не знает о типах. Продюсер обязан превратить объекты
ключа и значения в `byte[]` — этим занимаются сериализаторы, заданные при создании:

```java
new KafkaProducer<>(props, new StringSerializer(), jsonSerializer);
```

Встроенные: `StringSerializer`, `ByteArraySerializer`, `IntegerSerializer`,
`LongSerializer` и другие примитивы. Для структурированных данных — свой
сериализатор (`JsonSerde` в модуле `common`) или Avro/Protobuf с Schema Registry
(этап 4).

Порядок важен: сериализация происходит **до** партиционера, потому что дефолтный
партиционер хеширует уже сериализованные байты ключа.

Ошибка сериализации (`SerializationException`) — неретраебельная. Если объект
нельзя превратить в байты, повторять бессмысленно, запись отвергается сразу.

## 3. Партиционирование

### 3.1. Три случая

**Партиция указана явно.** Если в `ProducerRecord` задан номер партиции —
используется он, партиционер не вызывается.

**Ключ задан.** Дефолтный партиционер вычисляет:

```
partition = murmur2(serialized_key) % numPartitions
```

Детерминированно: один ключ всегда в одну партицию (пока число партиций не менялось).
Это механизм сохранения порядка по ключу из этапа 1.

**Ключ равен null.** Sticky-партиционер (KIP-480): продюсер выбирает одну партицию
и пишет туда, пока не сформируется батч, затем переключается. Плотнее набивает
батчи, чем round-robin.

### 3.2. Кастомный партиционер

Подключается через `partitioner.class`, реализует интерфейс `Partitioner`:

```java
public int partition(String topic, Object key, byte[] keyBytes,
                     Object value, byte[] valueBytes, Cluster cluster);
```

Типичные причины писать свой:
- Направить определённые ключи в выделенную партицию (VIP-обработка)
- Учесть неравномерность данных (борьба с «горячими» ключами)
- Особая бизнес-логика распределения

Заготовка с TODO — `CustomPartitioner` в модуле `02-producers`.

Осторожно: кастомный партиционер легко ломает балансировку. Если логика
направляет 80% трафика в одну партицию, эта партиция станет узким местом,
а её консьюмер — отстающим. См. контрольный вопрос про «горячие» ключи.

## 4. Аккумулятор и батчинг

### 4.1. Зачем батчить

Отправлять каждую запись отдельным сетевым запросом — расточительно: на каждый
запрос идут накладные расходы (заголовки протокола, round-trip по сети,
подтверждение). Kafka группирует записи в **батчи** по партициям и отправляет
батч целиком.

Батчинг — главный рычаг пропускной способности. Чем крупнее батч, тем меньше
запросов на то же число записей, тем выше throughput.

### 4.2. Механика накопления

Записи копятся в **record accumulator** — буфере в памяти. Для каждой партиции
свой батч. Батч отправляется, когда срабатывает любое из условий:

| Настройка | По умолчанию | Условие отправки батча |
|---|---|---|
| `batch.size` | 16384 (16 КБ) | Батч набрал этот размер (в байтах) |
| `linger.ms` | 0 | Прошло столько мс с момента первой записи в батч |

Взаимодействие тонкое:

- `linger.ms=0` (по умолчанию) — батч уходит, как только Sender освободится,
  не дожидаясь наполнения. Минимальная задержка, но батчи мельче.
- `linger.ms=10` — продюсер ждёт до 10 мс, давая батчу наполниться. Задержка
  растёт на единицы миллисекунд, throughput заметно выше под нагрузкой.

Важно: `linger.ms` не добавляет задержку, если трафик высокий — батч и так
наполнится до `batch.size` раньше таймера. Задержка проявляется только на редком
трафике, где батчу нечем наполниться.

### 4.3. Буфер и обратное давление

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `buffer.memory` | 33554432 (32 МБ) | Общий размер буфера аккумулятора |
| `max.block.ms` | 60000 | Сколько `send()` блокируется при полном буфере |

Если Sender не успевает отправлять (медленный брокер, сеть), буфер заполняется.
Когда он полон, `send()` **блокируется** до `max.block.ms`, затем бросает
`TimeoutException`. Это встроенное обратное давление: продюсер не даёт приложению
génерировать данные быстрее, чем они уходят.

Симптом переполнения буфера — `send()` начал блокироваться, хотя обычно мгновенный.
Причина почти всегда в брокере или сети, а не в самом буфере.

## 5. Компрессия

### 5.1. Как работает

`compression.type` сжимает **батч целиком** на стороне продюсера. Брокер хранит
батч сжатым и отдаёт консьюмеру сжатым — распаковывает консьюмер. Это часть
механизма zero-copy (этап 1): брокер не трогает содержимое.

| Тип | Степень сжатия | CPU | Когда |
|---|---|---|---|
| `none` | — | — | Данные уже сжаты (картинки, видео) |
| `lz4` | Средняя | Низкий | Хороший дефолт, баланс |
| `snappy` | Средняя | Низкий | Альтернатива lz4 |
| `zstd` | Высокая | Средний | Когда важен объём (сеть, диск), есть запас CPU |
| `gzip` | Высокая | Высокий | Максимум сжатия, редко оправдан |

### 5.2. Почему эффективность растёт с размером батча

Сжатие ищет повторы. В батче из сотен похожих записей (одинаковая структура JSON,
повторяющиеся поля) повторов много — сжатие даёт кратный выигрыш. В батче
из одной записи повторять почти нечего.

Отсюда синергия: `linger.ms` + компрессия работают вместе. Больше `linger.ms`
→ крупнее батчи → лучше сжатие → меньше трафика и места на диске.

Компрессия экономит трижды: сеть продюсер→брокер, место на диске, сеть
брокер→консьюмер. Цена — CPU на сжатие/распаковку.

## 6. acks и durability

### 6.1. Три уровня

`acks` определяет, в какой момент запись считается подтверждённой.

| `acks` | Продюсер ждёт | Скорость | Риск потери |
|---|---|---|---|
| `0` | ничего | макс. | любой сбой теряет запись |
| `1` | запись в лог лидера | средняя | потеря, если лидер упал до репликации |
| `all` (`-1`) | подтверждение всех реплик в ISR | ниже | минимальный |

### 6.2. acks=all не гарантирует сам по себе

Тонкость, связывающая с этапом 1: `acks=all` ждёт подтверждения от **текущего**
ISR. Если ISR схлопнулся до одного лидера, `all` означает «подтверждено одним
узлом» — не лучше, чем `acks=1`.

Гарантию даёт связка с `min.insync.replicas` (настройка топика/брокера):

```
acks=all + min.insync.replicas=2 + replication.factor=3
```

При такой конфигурации:
- Запись подтверждается минимум двумя репликами
- Если синхронных реплик меньше двух, запись отвергается (`NotEnoughReplicas`)
- Кластер переживает отказ одного брокера без потери данных и без остановки записи

Это стандарт для данных, которые нельзя терять. Настроен в `three-broker.yml`.

### 6.3. acks и идемпотентность

`acks=0` несовместим с идемпотентностью: она требует подтверждения, чтобы
отслеживать порядковые номера. При `enable.idempotence=true` (по умолчанию)
Kafka сама выставит `acks=all`.

## 7. Идемпотентность

### 7.1. Проблема, которую решает

При `max.in.flight.requests.per.connection > 1` и включённых ретраях возможно
переупорядочивание. Сценарий:

1. Продюсер шлёт батч A, затем B, не дожидаясь ответа на A.
2. Ответ на A теряется (сеть моргнула), но сам A записался.
3. B записывается.
4. Продюсер повторяет A → A ложится после B.

Результат: порядок B, A вместо A, B, плюс A может задвоиться (если первая запись
A всё-таки прошла).

### 7.2. Как чинит

Идемпотентный продюсер (`enable.idempotence=true`, по умолчанию в 4.x):

- Брокер присваивает продюсеру `producerId` (PID)
- Каждый батч на каждую партицию получает монотонный **sequence number**
- Брокер отслеживает последний записанный номер по каждому `(PID, партиция)`
- Дубликат с уже виденным номером — отбрасывается
- Батч с номером «через один» не принимается, пока не придёт пропущенный

Так обеспечивается **дедупликация и сохранение порядка** в пределах партиции,
даже при ретраях и `max.in.flight` до 5.

### 7.3. Границы гарантии

Идемпотентность действует:
- В пределах **одной партиции**
- В пределах **сессии продюсера** (перезапуск продюсера сбрасывает PID)

Идемпотентность НЕ даёт:
- Exactly-once через несколько партиций или топиков → транзакции (этап 5)
- Дедупликацию между перезапусками продюсера → транзакции с `transactional.id`
- Защиту от дублей на стороне консьюмера → идемпотентный консьюмер (этап 11)

### 7.4. Что включается автоматически

При `enable.idempotence=true` Kafka форсирует совместимые настройки:
- `acks=all`
- `max.in.flight.requests.per.connection <= 5`
- `retries > 0`

Если вы явно зададите несовместимое (например, `acks=1`), продюсер бросит
`ConfigException` при старте.

## 8. Обработка ошибок, ретраи, таймауты

### 8.1. Два класса ошибок

**Retriable** — временные, повтор может помочь: `NotLeaderOrFollower`
(сменился лидер), `NotEnoughReplicas`, сетевые таймауты, `RequestTimedOut`.
Продюсер повторяет их сам.

**Non-retriable** — повтор бессмыслен: `SerializationException`,
`RecordTooLarge`, `TopicAuthorization`. Сразу попадают в callback/Future
как ошибка.

### 8.2. Настройки ретраев и таймаутов

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `retries` | 2147483647 | Число повторов retriable-ошибок |
| `retry.backoff.ms` | 100 | Пауза между повторами |
| `delivery.timeout.ms` | 120000 | Общий бюджет времени на доставку записи |
| `request.timeout.ms` | 30000 | Таймаут одного запроса к брокеру |
| `max.block.ms` | 60000 | Блокировка `send()` при полном буфере |

Главная настройка — `delivery.timeout.ms`. Это верхняя граница всего:
от попадания в буфер до подтверждения или окончательной ошибки. Она включает
время в буфере, все ретраи и все `request.timeout.ms`. Именно её стоит крутить,
а не `retries`.

Соотношение, которое должно выполняться:

```
delivery.timeout.ms >= linger.ms + request.timeout.ms
```

### 8.3. Порядок при ретраях без идемпотентности

`max.in.flight.requests.per.connection` — сколько неподтверждённых запросов
к одному брокеру одновременно.

- Без идемпотентности + `max.in.flight > 1` + ретраи → риск переупорядочивания
  (раздел 7.1). Для строгого порядка без идемпотентности пришлось бы ставить
  `max.in.flight=1`, что бьёт по throughput.
- С идемпотентностью (по умолчанию) → `max.in.flight` до 5 безопасен,
  порядок сохраняется.

Это ответ на главный контрольный вопрос этапа: почему `max.in.flight > 1`
без идемпотентности опасен.

## 9. Синхронная и асинхронная отправка

### 9.1. Три способа

**Fire-and-forget** — отправил, не проверяешь результат:

```java
producer.send(record);
```

Максимальная скорость, но потерю не заметишь. Годится для метрик/логов при `acks=0/1`.

**Синхронно** — блокируешься до подтверждения:

```java
RecordMetadata md = producer.send(record).get();
```

`.get()` ждёт ответа брокера. Просто, но медленно: каждая запись — round-trip.
Throughput низкий. Применять, когда критичен порядок обработки результата
или нужна немедленная реакция на ошибку.

**Асинхронно с callback** — отправил, результат обработаешь в callback:

```java
producer.send(record, (metadata, exception) -> {
    if (exception != null) log.error("fail", exception);
    else log.info("p={} off={}", metadata.partition(), metadata.offset());
});
```

Лучший баланс: не блокируешься, но узнаёшь о результате. Основной способ
для production. Callback выполняется в Sender-потоке — не делайте в нём
тяжёлую или блокирующую работу.

### 9.2. flush и close

`producer.flush()` — блокируется, пока все батчи из буфера не отправлены.
Полезно перед завершением или в точке, где нужно гарантировать отправку.

`producer.close()` — flush + освобождение ресурсов. Вызывать обязательно
(try-with-resources), иначе последние батчи потеряются.

## 11. Ответы на контрольные вопросы

### 11.1. Почему `max.in.flight > 1` без идемпотентности переставляет записи?

При нескольких запросах «в полёте» одновременно и включённых ретраях повтор
упавшего запроса может обогнать следующий за ним, уже успешный. Пример: A и B
отправлены параллельно, ответ на A потерян, B записался, повтор A лёг после B —
порядок нарушен. Идемпотентность нумерует батчи и заставляет брокер восстанавливать
порядок по номерам, снимая проблему при `max.in.flight` до 5.

### 11.2. `acks=all` гарантирует, что данные не потеряются?

Сам по себе — нет. Он ждёт подтверждения от текущего ISR, а если ISR сжался
до одного лидера, гарантия вырождается в `acks=1`. Сохранность даёт связка
с `min.insync.replicas>=2` при `replication.factor>=3`: тогда запись требует
подтверждения минимум двух реплик, а при их нехватке отвергается, а не теряется.

### 11.3. Что делает `linger.ms=0` с пропускной способностью?

При `linger.ms=0` батч отправляется, как только освободится Sender, не дожидаясь
наполнения. Под высокой нагрузкой это не вредит (батч и так наполняется быстро),
но под редким трафиком батчи получаются мелкими, растёт число запросов и падает
throughput. Ненулевой `linger.ms` даёт батчу наполниться, повышая пропускную
способность ценой единиц миллисекунд задержки.

### 11.4. Чем `delivery.timeout.ms` отличается от `request.timeout.ms` и `retries`?

`request.timeout.ms` — таймаут одного запроса к брокеру. `retries` — число
повторов. `delivery.timeout.ms` — общий бюджет времени на всю доставку записи,
включающий время в буфере, все ретраи и все отдельные `request.timeout.ms`.
Это верхняя граница, которую видит приложение: по её истечении запись гарантированно
завершится успехом или ошибкой. Крутить для настройки надёжности следует именно
её, а не `retries`.

### 11.5. Что при переполнении `buffer.memory`?

Когда буфер аккумулятора заполнен (Sender не успевает отправлять), `send()`
перестаёт быть мгновенным и **блокируется** до `max.block.ms`. Если за это время
место не освободилось — бросает `TimeoutException`. Это встроенное обратное
давление: продюсер не даёт приложению генерировать данные быстрее, чем они
успевают уходить на брокер.
